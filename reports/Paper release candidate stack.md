# Paper Release Stack: Extract, Multilingual, Harden

Paper needs document extraction across all formats, multilingual support in totality, retrieval-quality improvements, release hardening, and an optional generative polish layer — all while keeping its local-first, single-~10-MB binary, no-telemetry, no-mandatory-cloud, and citation-guarantee invariants. This report synthesizes research across extraction, multilingual, retrieval quality, release hardening/security, and optional generation into a decision-ready plan. The bottom line: adopt a pure-Rust extraction stack (lopdf + docx-rs + calamine + pptxboss-core + rbook + mailparse) with OS-native OCR behind a feature flag; switch to multilingual-e5-small (384 dims, MIT, 100 languages) as the default embedding model with script-based segmentation; keep RRF(k=60) and exact sqlite-vec KNN, add structure-aware chunking and SQL metadata filters; defer generative polish from RC1 and build it post-release on user-supplied local servers. Blockers for RC are signed macOS/Windows artifacts, supply-chain CI gates (cargo-audit + cargo-deny + CycloneDX SBOM), copyleft-free licensing, parser isolation, robustness (WAL, atomic writes, integrity check), defined performance budgets, and an offline eval harness — everything else can wait.

## Extraction — pure-Rust defaults with gated native accelerators

Paper's extraction layer must be pure-Rust, permissively licensed, actively maintained, and buildable offline with no native dependencies, because Paper ships a single ~10 MB binary and forbids network downloads at build or runtime ([AGENTS.md — Build & test](file:///Users/p0is0n/GitHub/enzo/AGENTS.md); [AGENTS.md — paths](file:///Users/p0is0n/GitHub/enzo/AGENTS.md)). For PDF text extraction, lopdf (MIT/Apache-2.0, pure Rust) is the default: it extracts text per page (`Document::extract_text(&[page_numbers])`), giving page-scoped anchors for exact citations, bounds decompressed page size against zip bombs, and added ToUnicode CMap, AES rev 4, and PDFDocEncoding support in v0.34.0 ([crates.io/crates/lopdf](https://docs.rs/lopdf/latest/lopdf/struct.Document.html); [github.com/J-F-Liu/lopdf/blob/main/CHANGELOG.md](https://github.com/J-F-Liu/lopdf/blob/main/CHANGELOG.md)). pdfluent-extract 1.4.0 (MIT/Apache-2.0, builds on lopdf::Document) layers positioned text blocks and per-character bounding boxes on top when bbox fidelity is needed ([docs.rs/pdfluent-extract/latest/pdfluent_extract](https://docs.rs/pdfluent-extract/latest/pdfluent_extract)). pdf-extract 0.12.1 (MIT, pure Rust, ~8.8K SLoC, 95.7 KiB) is a simpler per-page fallback ([crates.io/crates/pdf-extract](https://crates.io/crates/pdf-extract); [docs.rs/pdf-extract/latest/pdf_extract/fn.extract_text_by_pages.html](https://docs.rs/pdf-extract/latest/pdf_extract/fn.extract_text_by_pages.html)). pdfium-render 0.9.5 (MIT/Apache-2.0, native binding to Google PDFium, 3.88 MiB crate, 262K SLoC) offers the highest-fidelity extraction plus page-to-image rendering for OCR fallback, but requires shipping/bundling the libpdfium shared library at runtime on all three OSes — a real deployment cost that breaks the single-binary ideal — so it must be feature-gated and off by default ([crates.io/crates/pdfium-render/0.9.5](https://crates.io/crates/pdfium-render/0.9.5); [github.com/ajrcarey/pdfium-render](https://github.com/ajrcarey/pdfium-render)). hayro 0.8.0 (Apache-2.0/MIT, pure Rust) is a page rasterizer, not a text extractor; it can feed an OCR fallback by rendering pages to bitmaps, but lacks encrypted-PDF support and cannot extract text natively ([crates.io/crates/hayro/0.8.0](https://crates.io/crates/hayro/0.8.0); [github.com/LaurenzV/hayro](https://github.com/laurenzv/hayro)). mupdf-rs / mupdf-sys 0.8.0 (AGPL-3.0) is explicitly ruled out: AGPL-3.0 violates Paper's permissive-license rule, and it requires a C/C++ toolchain plus libclang at build time ([crates.io/crates/mupdf/0.8.0](https://crates.io/crates/mupdf/0.8.0); [github.com/messense/mupdf-rs](https://github.com/messense/mupdf-rs)). A cross-cutting caveat: pure-Rust PDF extraction depends on `/ToUnicode` CMaps for reliable Unicode/CID mapping, reading order is not guaranteed by any pure-Rust crate (multi-column/interleaved text is a known weakness), and scanned/image-only PDFs return empty strings — OCR fallback is required ([webscraping.ai blog](https://webscraping.ai/blog/web-scraping-with-rust); [PDF Oxide text extraction](https://pdf.oxide.fyi/rust/docs/extraction/text)).

Office formats are well served by maintained pure-Rust crates under permissive licenses: docx-rs 0.4.22 (MIT, pure Rust, active through Jul 2026) reads DOCX paragraphs, runs, tables, headings, styles, headers/footers, footnotes, images, and TOC; it has no native page concept (DOCX is flow layout, so the anchor is paragraph/run order) ([lib.rs/docx-rs](https://lib.rs/docx-rs); [github.com/bokuweb/docx-rs/blob/main/CHANGELOG.md](https://github.com/bokuweb/docx-rs/blob/main/CHANGELOG.md); [docs.rs/docx-rs/latest/docx_rs](https://docs.rs/docx-rs/latest/docx_rs)). calamine (MIT, pure Rust) reads XLSX/XLS/XLSM/XLSB/XLA/XLAM/ODS with absolute `(row, column)` cell addressing and sheet names — a direct citation anchor as `SheetName!row:col` ([github.com/tafia/calamine](https://github.com/tafia/calamine); [docs.rs/calamine/latest/calamine/struct.Xlsx.html](https://docs.rs/calamine/latest/calamine/struct.Xlsx.html); [crates.io/crates/calamine](https://crates.io/crates/calamine)). pptxboss-core 0.3.0 / ppt-rs 0.2.37 (MIT or MIT/Apache-2.0, pure Rust) read PPTX and legacy PPT (MS-CFB/MS-PPT/MS-ODRAW) with per-slide text and slide numbers as the citation anchor (`slide.number()`) ([crates.io/crates/pptxboss-core/0.3.0](https://crates.io/crates/pptxboss-core/0.3.0); [crates.io/crates/ppt-rs/0.2.37](https://crates.io/crates/ppt-rs/0.2.37); [github.com/longway-code/rustypptx](https://github.com/longway-code/rustypptx); [crates.io/crates/pptx](https://crates.io/crates/pptx)). rbook 0.7.12 (Apache-2.0, pure Rust) reads EPUB 2/3 with OPF metadata, manifest, spine reading order, and ToC; anchor is spine document index + href + optional fragment ([docs.rs/rbook](https://docs.rs/rbook); [github.com/DevinSterling/rbook](https://github.com/DevinSterling/rbook)). mailparse 0.18.0 (0BSD, pure Rust, MSRV 1.85) and mail-parser (stalwartlabs, zero-copy, fuzzed) handle MIME/mbox email; msg_parser 0.3.6 (MIT) handles Outlook .msg ([crates.io/crates/mailparse/0.18.0](https://crates.io/crates/mailparse/0.18.0); [crates.io/crates/mail-parser](https://crates.io/crates/mail-parser); [crates.io/crates/msg_parser/0.3.6](https://crates.io/crates/msg_parser/0.3.6)). ZIP/TAR via the standard zip and tar crates (pure Rust, MIT/Apache-2.0) cover archives ([docs.rs/omniparse supported formats](https://docs.rs/omniparse/latest/omniparse/)). HTML boilerplate removal has several pure-Rust options (libreadability, dom_smoothie 0.19.0, legible, rs-trafilatura, justext-rs, decruft 0.2) ([docs.rs/libreadability](https://docs.rs/libreadability); [crates.io/crates/dom_smoothie](https://crates.io/crates/dom_smoothie); [github.com/ryanfowler/legible](https://github.com/ryanfowler/legible); [github.com/Murrough-Foley/rs-trafilatura](https://github.com/Murrough-Foley/rs-trafilatura); [crates.io/crates/justext](https://crates.io/crates/justext); [crates.io/crates/decruft](https://crates.io/crates/decruft)).

Not viable or unsupported: legacy binary .DOC and .PPT (OLE compound) have no maintained pure-Rust reader — mark as unsupported without LibreOffice shell-out ([crates.io/crates/rtf-parser](https://docs.rs/crate/rtf-parser/latest); [crates.io/crates/rtf-parser-tt](https://crates.io/crates/rtf-parser-tt); [crates.io/crates/scrivener-rtf](https://crates.io/crates/scrivener-rtf); [rclip-rtf prior-art review](https://crates.io/crates/rclip-rtf)). ODT (text) and ODP (presentation) are not covered — calamine covers ODS (spreadsheet) only ([github.com/tafia/calamine](https://github.com/tafia/calamine)). RTF has no clearly production-grade parser; rtf-parser 0.4.3 panics on lone surrogates and cannot ingest code-page RTF bytes, and rtf-parser-tt 0.6.0 is an unproven fork ([crates.io/crates/rtf-parser](https://docs.rs/crate/rtf-parser/latest); [crates.io/crates/rtf-parser-tt](https://crates.io/crates/rtf-parser-tt)). docx-rs is "designed for construction, not consumption" per Tritium's experience — a caution for deeply nested tables, not a blocker for read-only extraction ([tritium.legal/blog/word](https://tritium.legal/blog/word)).

For OCR of scanned/image-only PDFs and photos, treat OCR as optional and gated off by default, consistent with invariant #1 (missing weights mean keyword-only search plus a hint) ([AGENTS.md — Invariants](file:///Users/p0is0n/GitHub/enzo/AGENTS.md)). Pure-Rust OCR is immature: ocrs 0.14.0 (Apache-2.0/MIT, ~347K downloads) is Latin/English only, "early preview," and downloads models on first run, violating the fully-local rule unless pre-bundled ([github.com/robertknight/ocrs](https://github.com/robertknight/ocrs); [crates.io/crates/ocrs](https://crates.io/crates/ocrs); [docs.rs/ocrs/latest/ocrs](https://docs.rs/ocrs/latest/ocrs)). The pragmatic answer is OS-native OCR behind a small trait abstraction: apple-vision 0.17.1 (MIT/Apache-2.0, macOS 13+, Xcode SDK build-only) on macOS ([crates.io/crates/apple-vision/0.17.1](https://crates.io/crates/apple-vision/0.17.1); [github.com/doom-fish/vision-rs](https://github.com/doom-fish/vision-rs)); Windows.Media.OCR on Windows (no mature Rust crate found — a gap requiring interop or Tesseract fallback); Tesseract via kreuzberg-tesseract 1.0.0-rc.1 (maintained fork, C++17 toolchain, static linking default, tessdata language files) on Linux and as the multi-language fallback ([crates.io/crates/kreuzberg-tesseract](https://crates.io/crates/kreuzberg-tesseract); [crates.io/crates/tesseract5-rs/0.1.4](https://crates.io/crates/tesseract5-rs/0.1.4)). uni-ocr 0.1.5 (MIT/Apache-2.0) demonstrates the multi-provider abstraction pattern (macOS VisionKit, Windows OCR, Tesseract, cloud gated out) but has light repo activity ([github.com/screenpipe/uniOCR](https://github.com/screenpipe/uniOCR); [crates.io/crates/uni-ocr/0.1.5](https://crates.io/crates/uni-ocr/0.1.5)). Render page to bitmap (pdfium-render or hayro) then OCR; accuracy on receipts/low-res photos is unmeasured for every engine in scope.

Canonical anchoring for formats without lines: PDF = page N (1-indexed, matching lopdf/pdfluent-extract); spreadsheets = `SheetName!row:col` (calamine absolute coordinates); presentations = slide N (pptxboss-core); DOCX = paragraph/run ordinal or byte offset (no native page); EPUB = spine document index + href + optional fragment (rbook); email = Message-ID + body part index, mbox = message index within file; HTML/Markdown/plain text = line_start/line_end as today, byte offset secondary ([docs.rs/lopdf](https://docs.rs/lopdf/latest/lopdf/struct.Document.html); [docs.rs/pdfluent-extract](https://docs.rs/pdfluent-extract/latest/pdfluent_extract); [docs.rs/calamine](https://docs.rs/calamine/latest/calamine/struct.Range.html); [crates.io/crates/pptxboss-core](https://crates.io/crates/pptxboss-core/0.3.0); [docs.rs/rbook](https://docs.rs/rbook/latest/rbook/epub)). The hit/hydration layer should carry an optional format-specific anchor field so citations resolve without inventing line numbers; the internal page-indexing convention (0- vs 1-based) is an open gap ([docs.rs/pdfluent-extract](https://docs.rs/pdfluent-extract/latest/pdfluent_extract)).

Shell-out to pdftotext (Poppler), textutil (macOS), and LibreOffice headless are supplements, not replacements — each introduces a hard system dependency, breaks the single-binary guarantee, complicates PAPER_OFFLINE=1 deployments, and makes exact citation anchoring harder to control ([github.com/rainrambler/PDFBench](https://github.com/rainrambler/PDFBench); [github.com/morganlinton/Albatross/blob/main/.github/workflows/release.yml](https://github.com/morganlinton/Albatross/blob/main/.github/workflows/release.yml)). Keep pure-Rust crates as default; expose shell-out accelerators only behind opt-in feature flags/config with graceful degradation to a hint when the binary is absent ([AGENTS.md — Invariants](file:///Users/p0is0n/GitHub/enzo/AGENTS.md)).

Binary-size impact: the recommended pure-Rust stack adds modest size and stays within the ~10 MB release budget; docx-rs 0.4.22 source is 3.0 MB (mostly XML schema, not compiled binary impact) ([crates.io/crates/docx-rs/0.4.22](https://crates.io/crates/docx-rs/latest)). The main risks are optional native paths: pdfium-render (3.88 MiB crate + runtime libpdfium) and Tesseract bindings (several MB static + tessdata per language) — both strictly feature-gated and off by default ([crates.io/crates/pdfium-render/0.9.5](https://crates.io/crates/pdfium-render/0.9.5); [crates.io/crates/kreuzberg-tesseract](https://crates.io/crates/kreuzberg-tesseract)). No per-crate binary-size baseline or budget has been measured yet (gap).

## Multilingual — segmentation, stemming, one cross-lingual model, no small multilingual reranker

SQLite FTS5's unicode61 tokenizer is inadequate for any non-space-delimited script: Chinese, Japanese, Thai, Khmer, Lao, and Burmese are indexed as one giant token per contiguous run (CJK characters are all "alphanumeric" to unicode61), so phrase/AND queries like `MATCH '魚池'` miss documents such as `南投縣魚池鄉` ([emDash issue #2245/#2775](https://github.com/emdash-cms/emdash/issues/2245); [emDash issue #2775](https://github.com/emdash-cms/emdash/issues/2775); [NousResearch/hermes-agent issue #14829](https://github.com/NousResearch/hermes-agent/issues/14829)). The fix is app-side segmentation run at both index and query time: icu_segmenter for Thai/Khmer/Lao/Burmese word breaking (Unicode #29 + dictionary/LSTM, gated behind compiled_data) ([icu_segmenter docs](https://docs.rs/icu_segmenter/latest/icu_segmenter/struct.WordSegmenter.html); [icu_segmenter 2.4.0](https://doc.servo.org/icu_segmenter/struct.WordSegmenter.html); [icu::segmenter docs](https://docs.rs/icu/latest/icu/segmenter/struct.WordSegmenter.html)), lindera (IPADIC/UniDic) for Japanese ([Lindera docs](https://lindera.github.io/lindera/); [GitHub lindera/lindera](https://github.com/lindera/lindera); [SIH/lindera-dicts](https://huggingface.co/datasets/SIH/lindera-dicts); [lindera-ipadic lib.rs](https://lib.rs/crates/lindera-ipadic); [lindera-sudachidict lib.rs](https://lib.rs/crates/lindera-sudachidict)), and jieba-rs for Chinese ([jieba-rs crates.io](https://crates.io/crates/jieba-rs); [messense/jieba-rs GitHub](https://github.com/messense/jieba-rs)). tantivy/unicode-segmentation and trigram are cheap fallbacks only — trigram is not CJK-aware (character n-grams, no word semantics) and inflates the index ([Audrey Roy Greenfeld FTS5 tokenizers](https://audrey.feldroy.com/articles/2025-01-13-SQLite-FTS5-Tokenizers-unicode61-and-ascii); [NousResearch cjk_unicode61 commit](https://github.com/NousResearch/hermes-agent/commit/b10952e9c6fc165a1a71b52798ddb6fc8482c1c4)). Line citation accuracy is preserved regardless of tokenizer choice because Paper chunks are line-accurate; tokenization only affects which terms index a given line range ([AGENTS.md — Layout](file:///Users/p0is0n/GitHub/enzo/AGENTS.md)).

Paper's pipeline hardcodes `porter unicode61` (Porter2 English stemmer) for every language, which actively harms non-English recall: stemming Japanese/Chinese/Thai (no inflection), Arabic (nonconcatenative root-and-pattern), and agglutinative languages (Turkish, Finnish, Hungarian) either does nothing useful or destroys terms ([emDash issue #2245](https://github.com/emdash-cms/emdash/issues/2245); [Audrey Roy Greenfeld FTS5 tokenizers](https://audrey.feldroy.com/articles/2025-01-13-SQLite-FTS5-Tokenizers-unicode61-and-ascii)). Drop porter as the default for all languages; keep it only for English. For everything else use plain unicode61 with `remove_diacritics=1` ([SQLite FTS5 unicode61 docs](https://www.sqlite.org/fts5.html#the_unicode61_tokenizer)). Per-language stemming via Snowball (rust `stemmer` crate) covers ~25 languages including Arabic, French, German, Spanish, Russian, but NOT Chinese/Japanese/Korean/Thai/Vietnamese, where no stemming is correct ([SQLite FTS5 unicode61 docs](https://www.sqlite.org/fts5.html#the_unicode61_tokenizer)). Stemming must be applied identically at index and query time, and only on the FTS5 side (sqlite-vec embeddings are not stemmed).

The strongest fit for Paper's 384-dim sqlite-vec schema and <=200 MB default budget is intfloat/multilingual-e5-small: MIT license, ungated, 384 dims, 100 languages, BERT architecture loadable by Candle (~112-134 MB quantized, ~470 MB F32) ([HF API intfloat/multilingual-e5-small](https://huggingface.co/api/models/intfloat/multilingual-e5-small); [Teradata/multilingual-e5-small](https://huggingface.co/Teradata/multilingual-e5-small)). sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2 (Apache-2.0, 384 dims, ~118 MB params, 50+ languages) is the Apache-licensed fallback but is slightly weaker on retrieval MTEB and covers fewer languages ([HF API sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2](https://huggingface.co/api/models/sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2)). LaBSE (768 dims, ~1.1 GB), jina-embeddings-v3 (non-standard architecture, configurable dims, ~0.5 GB+), snowflake-arctic-embed (English-only), and multilingual-e5-base (768 dims, ~487 MB) are NOT viable: wrong dims, too large, non-BERT architecture, or English-only ([HF API model-index intfloat/multilingual-e5-small](https://huggingface.co/api/models/intfloat/multilingual-e5-small)). ONE multilingual model for everyone is the only option within the <=200 MB default budget; language-tiered downloads multiply the budget, complicate the hash-pinned spec invariant, and no per-language model beats a good multilingual one enough to justify separate downloads ([AGENTS.md — Model integration tests](file:///Users/p0is0n/GitHub/enzo/AGENTS.md)). If even ~112 MB is too much, the existing invariant holds: missing weights → keyword-only (FTS5) search plus a hint, or exit code 3 with --semantic ([AGENTS.md — Invariants](file:///Users/p0is0n/GitHub/enzo/AGENTS.md)). Segmentation dictionaries (jieba Chinese, lindera Japanese, icu_segmenter Thai/Khmer/Lao/Burmese) add their own MB on top of the embedding model — this is the real budget pressure ([jieba-rs crates.io](https://crates.io/crates/jieba-rs); [Lindera docs](https://lindera.github.io/lindera/); [icu_segmenter docs](https://docs.rs/icu_segmenter/latest/icu_segmenter/struct.WordSegmenter.html)).

No ungated multilingual cross-encoder reranker exists small enough for Paper's budget. BAAI/bge-reranker-v2-m3 (Apache-2.0, 568M params, 2.27 GB FP32, XLM-RoBERTa-Large, 8K context) is the canonical multilingual reranker but vastly exceeds even the opt-in budget (bge-reranker-base is 1.13 GB English/Chinese only); bge-reranker-v2-gemma (~10 GB) and v2-minicpm-layerwise (~10.9 GB) are far too large ([BGE docs bge_reranker_v2](https://bge-model.com/bge/bge_reranker_v2.html); [ai-opensource.com](https://ai-opensource.com/models/bge-reranker-v2-m3/); [BGE docs](https://bge-model.com/bge/bge_reranker_v2.html)). Keep bge-reranker-base as opt-in reranker for English/Chinese and document v2-m3 as user-downloadable but not shipped; do NOT bundle a multilingual reranker in the default binary ([BGE docs model list](https://huggingface.co/BAAI/bge-reranker-v2-m3)).

Replace "400 words" chunking with a sentence-aware chunker: split on ICU BreakIterator sentence boundaries (Unicode #29, which knows CJK terminators U+3002 ideographic full stop, U+FF01, U+FF1F), pack sentences into chunks bounded by a max token/character count (~512 tokens to match embedding context), and snap chunk ends to line boundaries so citations stay exact ([ICU Boundary Analysis](https://unicode-org.github.io/icu/userguide/boundaryanalysis/); [tidycjk cjk_sentences](https://cran.r-project.org/web/packages/tidycjk/tidycjk.pdf); [icu_segmenter docs](https://docs.rs/icu_segmenter/latest/icu_segmenter/)). Word-count chunking is invalid for CJK/Thai where words are not space-delimited. For Thai/Lao/Khmer, ICU sentence segmentation is approximate; treat paragraph/newline as a hard chunk boundary as fallback ([ICU Boundary Analysis Dictionary-Based BreakIterator](https://unicode-org.github.io/icu/userguide/boundaryanalysis/)). Token-count vs character-count sizing for CJK and concrete max-tokens-per-chunk default are open gaps.

For query-time language detection, lingua (pemistahl/lingua-rs) is the most accurate Rust detector but accuracy drops significantly below ~120 characters and it has a large binary/data footprint ([lingua-rs GitHub](https://github.com/pemistahl/lingua-rs); [docs.rs lingua 1.3.2](https://docs.rs/crate/lingua/1.3.2/source/README.md); [Lingua 1.5.0 announcement](https://query.rs/posts/2023-06-15/149viv4/lingua-1-5-0-the-most-accurate-natural-language-detection-library-for-rust-now-w)). whatlang is ~15x faster and ~180x smaller but weaker (single words 57%, word pairs 71%, sentences 94% vs Lingua 74%/89%/96%) ([whatlang crates.io](https://crates.io/crates/whatlang); [whatlang.org](https://whatlang.org/)). whichlang (quickwit) is fast and accurate on short texts ([whichlang GitHub](https://github.com/quickwit-oss/whichlang); [Quickwit blog](https://quickwit.io/blog/whichlang-language-detection-library)). None is reliable on single words; detection is a hint, not a hard gate. Script-based detection (Unicode script: Hiragana/Katakana=Japanese, Han=Chinese, Thai script=Thai, Myanmar=Burmese, Khmer=Khmer, Lao=Lao) is 100% accurate on script-identifiable text and zero-cost; combine with lingua for Latin-script languages ([ICU Boundary Analysis](https://unicode-org.github.io/icu/userguide/boundaryanalysis/)). cld3 has no mature maintained Rust binding; emk/rust-cld2 is CLD2 (older, C++ binding) — not recommended for a single-static-binary project ([lingua-rs README](https://docs.rs/crate/lingua/1.3.2/source/README.md)).

Apply the same normalization pipeline at index and query time: NFC/NFKC → case folding → diacritic stripping (unicode61 remove_diacritics=1 handles FTS5 side) → full/half-width normalization (CJK) → Arabic/Indic digit normalization ([SQLite FTS5 unicode61 docs](https://www.sqlite.org/fts5.html#the_unicode61_tokenizer); [Unicode Normalization TR15](https://unicode.org/reports/tr15/)). The unic Rust crate provides Unicode normalization/categories/case folding ([unic crates.io](https://crates.io/crates/unic)). Do NOT strip diacritics blindly for languages where they are phonemic (Arabic, Vietnamese, Indic); RTL (Arabic/Hebrew) is display-only for search. Emoji should be preserved as tokens, not stripped. NFKC matters for CJK to resolve full/half-width and compatibility characters ([unicode61 categories option](https://www.sqlite.org/fts5.html#the_unicode61_tokenizer)). The unic crate version/maintenance status and the confirmed list of languages where diacritic stripping is harmful are open gaps.

For stopwords, stop_words (cmccomb/rust-stop-words, v0.10.1) is the best Rust crate: ISO 639-1 + NLTK lists, static slices, no allocation, feature-gated (iso default), covers ~60+ languages including zh, ja, th, ar, hi ([stop_words docs.rs](https://docs.rs/stop-words/latest/stop_words/); [crates.io stop-words 0.10.1](https://crates.io/crates/stop-words); [stop_words Language Coverage Table](https://docs.rs/stop-words/latest/stop_words/)). It does NOT cover km (Khmer), lo (Lao), my (Burmese) — exactly Paper's hardest segmentation languages also lack stopword lists ([stop_words coverage table](https://docs.rs/stop-words/latest/stop_words/)). Stopwords are optional in Paper (FTS5 can index everything; stopword removal is a relevance optimization), so shipping stopword data for ~20 major languages and skipping the rest is acceptable ([stop_words docs.rs](https://docs.rs/stop-words/latest/stop_words/)). Exact binary size added by stop_words iso feature and whether to integrate stopwords into FTS5's tokenizer vs filter at pipeline level are open gaps.

Evaluation: use MIRACL (18 languages, 726k judgments, 78k queries, Wikipedia, native-speaker annotated, Apache-2.0, metrics nDCG@10 and Recall@100) and Mr. TyDI (11 languages, human-labeled) as primary multilingual retrieval benchmarks; MTEB for embedding leaderboard positioning; CLIRMatrix (139 languages, synthetic BM25-derived labels) is NOT recommended — its query titles are short named entities and labels are biased toward lexical approaches ([MIRACL TACL paper](https://aclanthology.org/2023.tacl-1.63/); [project-miracl/miracl GitHub](https://github.com/project-miracl/miracl); [Mr. TyDI arxiv 2108.08787](https://arxiv.org/abs/2108.08787); [CLIRMatrix comparison](https://aclanthology.org/2023.tacl-1.63/)). Build a small reproducible local corpus (3-5 language Wikipedia subset, EN+JA+TH+AR+SW, ~10k passages each, 50-100 hand-labeled queries per language) because MIRACL/Mr. TyDI corpora are huge (up to 32.9M passages for EN) and require network — conflicting with Paper's no-network testing invariant ([MIRACL TACL paper](https://aclanthology.org/2023.tacl-1.63/); [Mr. TyDI arxiv 2108.08787](https://arxiv.org/abs/2108.08787)). MIRACL per-language nDCG@10 baselines for multilingual-e5-small and a concrete recipe for the local corpus are open gaps ([HF API model-index intfloat/multilingual-e5-small](https://huggingface.co/api/models/intfloat/multilingual-e5-small)).

## Retrieval quality — structure-aware chunking, keep RRF and exact KNN, metadata filters, evaluation harness

Structure-aware chunking (headings/page/paragraph boundaries) is the highest-value chunking change for household documents (warranties, receipts, tax PDFs, manuals): it prevents mid-sentence/mid-table cuts that break citation line accuracy and retrieval relevance ([What is Chunking in RAG?](https://theaiengineer.substack.com/p/what-is-chunking); [Splunk: Advanced Chunking Techniques](https://www.splunk.com/en_us/blog/artificial-intelligence/chunking-techniques.html)). Split on H1/H2/# headings or PDF page boundaries, then cap at ~400 words with 40-word overlap, and populate `page` from PDF text extraction if a PDF extractor is added — otherwise page stays 0 and citations say `path:L-L` ([What is Chunking in RAG?](https://theaiengineer.substack.com/p/what-is-chunking)). Semantic chunking, late chunking (requires long-context encoders, not a drop-in for sqlite-vec single-vector schema), and ColBERT/flashrank (need multi-vector non-SQLite storage) are NOT worth the complexity for small household corpora ([Late Chunking: Contextual Chunk Embeddings](https://arxiv.org/html/2409.04701v1); [colsearch](https://github.com/ddickmann/colsearch); [Late Chunking arxiv](https://arxiv.org/html/2409.04701v1)). Parent-child / small-to-big retrieval is valuable for answers needing a whole clause, but Paper's answers are extractive and do not consume expanded context, so defer until answers quote multiple chunks ([Advanced RAG 01: Small-to-Big Retrieval](https://medium.com/data-science/advanced-rag-01-small-to-big-retrieval-172181b396d4); [Dify parent-child retrieval](https://dify.ai/blog/introducing-parent-child-retrieval-for-enhanced-knowledge)). No measured data yet on how much structure-aware chunking changes nDCG/recall for a household corpus — the eval harness must quantify this ([src/core/index/indexer](file:///Users/p0is0n/GitHub/enzo/src/core/index/indexer.rs)).

Keep RRF(k=60) fusion: it is rank-based and avoids the score-incompatibility problem of naively averaging unbounded BM25 with bounded cosine ([Hybrid Search: BM25, Vector & Reranking Reference 2026](https://digitalapplied.com/blog/hybrid-search-bm25-vector-reranking-reference-2026); [Qdrant Hybrid Search](https://qdrant.tech/documentation/search-tuning/hybrid-search); [src/core/search/pipeline.rs rrf_fuse](file:///Users/p0is0n/GitHub/enzo/src/core/search/pipeline.rs)). Weighted score fusion (α-normalized) is sensitive to BM25/cosine normalization and solves a problem RRF already addresses ([arxiv 2608.00452v1](https://arxiv.org/html/2608.00452v1)). The risky part is the early exit "skip semantic if >=10 keyword hits": for household docs this is often harmful because a short receipt/invoice can produce 10+ keyword hits on stopword-ish OR terms while the truly relevant document (different wording, no shared keywords) gets zero semantic consideration ([Hybrid Search: BM25, Vector & Reranking Reference 2026](https://digitalapplied.com/blog/hybrid-search-bm25-vector-reranking-reference-2026)). Exit only when the top keyword hit has High confidence (full term coverage) or semantic already ran; never skip semantic purely on keyword count. BEIR hybrid benchmarks show keyword+dense on a single SQLite stack is competitive (nDCG@10 differing by at most 0.0091) ([xerj benchmarks](https://raw.githubusercontent.com/xerj-org/xerj/main/benchmarks/query-1-2026-11/README.md)). Sweeping the keyword_sufficiency_threshold in {0, 5, 10, 20} needs the eval harness ([src/core/search/tier0.rs fts5_match_expr](file:///Users/p0is0n/GitHub/enzo/src/core/search/tier0.rs)).

Keep exact brute-force sqlite-vec KNN: for household corpora (hundreds to low-thousands of 384-dim chunks) exact scan is single-digit to tens of milliseconds, well within interactive latency ([SimpleVecDB benchmarks](https://github.com/CoderDayton/SimpleVecDB/blob/main/docs/benchmarks.md); [2ndbrain ADR 0001](https://github.com/apresai/2ndbrain/blob/main/docs/adr/0001-vector-search.md)). Only consider ANN/quantization if measurement shows >100 ms p95 at the target corpus size, and only if it stays a single-file SQLite extension ([sqlite-vec benchmarks-ann](https://github.com/asg017/sqlite-vec/blob/main/benchmarks-ann/README.md); [basic-memory issue #1996](https://github.com/basicmachines-co/basic-memory/issues/1996); [sqlite-vector](https://github.com/sqliteai/sqlite-vector)). USearch/hnsw_rs/Qdrant edge/LanceDB introduce a second storage file or separate process, breaking the single-file SQLite invariant ([sqlite-vec benchmarks-ann](https://github.com/asg017/sqlite-vec/blob/main/benchmarks-ann/README.md)). int8 quantization (~13× speedup, ~99.5% recall) is the only quantization worth keeping in reserve; 1-bit (10% recall) is unacceptable for citation-correct search ([sqlite-vector](https://github.com/sqliteai/sqlite-vector)). No measured p95 latency for Paper's exact KNN at realistic household corpus sizes — add a bench target (p95 < 50 ms at 10k chunks) to CI ([AGENTS.md — Layout](file:///Users/p0is0n/GitHub/enzo/AGENTS.md)).

Add metadata filters (file type, path root, mtime/date range) as SQL WHERE clauses on the existing `chunks` table before KNN/FTS5 — cheap and directly useful for household queries ("tax PDFs from 2025", "warranties in /Manuals") ([src/core/search/tier1.rs](file:///Users/p0is0n/GitHub/enzo/src/core/search/tier1.rs); [src/core/index/schema.rs](file:///Users/p0is0n/GitHub/enzo/src/core/index/schema.rs)). `mtime` is already indexed per chunk; a `--before`/`--after` date filter or `ext:pdf` filter is a WHERE clause addition to tier0/tier1 SQL, low complexity, high usefulness ([src/core/index/schema.rs](file:///Users/p0is0n/GitHub/enzo/src/core/index/schema.rs)). Document-level aggregation conflicts with Paper's exact-citation invariant (every hit carries path+line_start+line_end); keep chunk-level hits ([AGENTS.md — Invariants](file:///Users/p0is0n/GitHub/enzo/AGENTS.md)). Recency weighting is a relevance signal, not a filter; an old manual is still the correct answer to "how do I reset the fridge" — avoid by default, expose only as an opt-in config knob if eval shows benefit ([AGENTS.md — project context](file:///Users/p0is0n/GitHub/enzo/AGENTS.md)). No query-language design yet for filters (`receipts after:2025-01-01` vs `--after` flag) — needs CLI/MCP design separate from retrieval-quality research ([src/core/search/tier1.rs](file:///Users/p0is0n/GitHub/enzo/src/core/search/tier1.rs)).

Do NOT add query expansion or an LLM-based query rewriter: adds a model, non-determinism, and breaks the extractive/no-LLM invariant ([AGENTS.md invariants](file:///Users/p0is0n/GitHub/enzo/AGENTS.md)). Add lightweight deterministic handling only: preserve quoted phrases and identifiers as exact FTS5 terms (already double-quoted), stopword-aware OR handles natural-language questions ([src/core/search/tier0.rs STOPWORDS](file:///Users/p0is0n/GitHub/enzo/src/core/search/tier0.rs); [AGENTS.md invariants](file:///Users/p0is0n/GitHub/enzo/AGENTS.md)). Defer spelling tolerance/fuzzy search — household documents contain exact identifiers (invoice/model numbers) where fuzzy matching can surface wrong docs ([AGENTS.md — project context](file:///Users/p0is0n/GitHub/enzo/AGENTS.md)). Numeric range and date filtering belong in metadata filters, not the embedding/keyword query; amounts over $500 require structured extraction, not query understanding ([src/core/search/tier0.rs](file:///Users/p0is0n/GitHub/enzo/src/core/search/tier0.rs)). bge-small/e5 embeddings already encode semantic tolerance for paraphrase, so query expansion gives diminishing returns ([AGENTS.md — Layout](file:///Users/p0is0n/GitHub/enzo/AGENTS.md)). No amount/currency extraction from receipts exists yet — see Aggregation section ([src/core/index/indexer.rs](file:///Users/p0is0n/GitHub/enzo/src/core/index/indexer.rs)).

Do NOT add text-to-SQL or a local LLM for aggregation questions — both break the extractive/no-generative invariant and add model weight ([AGENTS.md invariants](file:///Users/p0is0n/GitHub/enzo/AGENTS.md); [LlamaIndex: Combining Text-to-SQL with Semantic Search](https://www.llamaindex.ai/blog/combining-text-to-sql-with-semantic-search-for-retrieval-augmented-generation-c60af30ec3b); [Review of LLM-based Text-to-SQL Systems](https://arxiv.org/html/2410.01066v2)). Instead: deterministic field extraction at index time (merchant, date, amount, warranty/expiry dates via regex over chunk text into a structured `metadata`/sidecar table) + SQL aggregation for "list every warranty and expiry" / "total spent on appliances 2025", with RAG only providing citations/explanation ([HuggingFace discuss: Local Document RAG System](https://discuss.huggingface.co/t/help-with-a-local-document-rag-system-storage-ingestion-query-highlighting/176993); [Reddit: Will RAG be effective or text-to-SQL?](https://www.reddit.com/r/LangChain/comments/1j7uu82/will_rag-be-effective-for-my-use-case-or-should-i/)). The `chunks.metadata` column already exists as `'{}'` JSON in indexer.rs — a natural place to store extracted fields, or a separate sidecar table keyed by chunk id ([src/core/index/indexer.rs](file:///Users/p0is0n/GitHub/enzo/src/core/index/indexer.rs)). Extraction rules (what counts as "appliance", date formats, currency symbols) and a SQL aggregation surface in CLI/MCP are not yet defined ([src/core/index/indexer.rs](file:///Users/p0is0n/GitHub/enzo/src/core/index/indexer.rs)).

Keep the cross-encoder reranker (bge-reranker-base, opt-in, 1.13 GB) restricted to top ~20 fused candidates and measure its actual nDCG/MRR delta before making it default ([Rerankers Aren't Magic Either](https://towardsdatascience.com/rerankers-arent-magic-either-when-the-cross-encoder-layer-is-worth-the-cost-enterprise-document-intelligence-vol-1-2bis); [zk2 ADR 0016](https://github.com/zk2/zk2-rag-platform/blob/main/docs/adr/0016-cpu-reranking.md); [Qdrant: When Is a Reranker Worth It?](https://qdrant.tech/documentation/search-tuning/when-a-reranker-is-worth-it/)). Cross-encoders read query+candidate together and output a single relevance score per pair; tens of milliseconds per pair on CPU — reranking 20 candidates is acceptable, reranking everything is not ([zk2 ADR 0016](https://github.com/zk2/zk2-rag-platform/blob/main/docs/adr/0016-cpu-reranking.md)). ColBERT/flashrank are NOT worth it: multi-vector MaxSim scoring and non-SQLite storage break the single-file invariant ([colsearch](https://github.com/ddickmann/colsearch); [Late Chunking arxiv](https://arxiv.org/html/2409.04701v1)). CPU latency target: reranking 20 pairs well under ~500 ms on a desktop CPU ([zk2 ADR 0016](https://github.com/zk2/zk2-rag-platform/blob/main/docs/adr/0016-cpu-reranking.md)). No measured nDCG/MRR delta from the cross-encoder on Paper's household corpus — the eval harness must compare RRF-only vs RRF+rerank ([src/core/search/pipeline.rs confidence_for](file:///Users/p0is0n/GitHub/enzo/src/core/search/pipeline.rs)).

Build an offline, CI-runnable eval harness in the repo using the deterministic HashEmbedder (already in tests/common/mod.rs) plus a small hand-labeled household-doc golden set ([AGENTS.md — Layout](file:///Users/p0is0n/GitHub/enzo/AGENTS.md); [tests/common/mod.rs](file:///Users/p0is0n/GitHub/enzo/tests/common/mod.rs)). Metrics: recall@k, MRR, nDCG@10, citation accuracy (path+line resolve to real content), and abstention correctness (Correct Abstention Rate on unanswerable questions) ([JSLEEKR/ragcheck](https://github.com/JSLEEKR/ragcheck); [tahasiddiquii/hybrid-graph-rag](https://github.com/tahasiddiquii/hybrid-graph-rag); [anbsamsam17/hybrid-rag-pipeline](https://github.com/anbsamsam17/hybrid-rag-pipeline); [paiteq-ai/rag-bench-2026q2](https://huggingface.co/datasets/paiteq-ai/rag-bench-2026q2)). Corpus: ~50-200 household documents (warranties, receipts, tax PDFs, manuals; mix of PDFs and plain text/markdown), few thousand chunks, so exact KNN stays fast and the harness runs in CI ([AGENTS.md — Invariants](file:///Users/p0is0n/GitHub/enzo/AGENTS.md)). Question types: exact identifier (tests keyword early exit), paraphrase (tests semantic), cross-lingual (tests multilingual-e5 opt-in), aggregation (tests structured extraction), unanswerable (tests abstention) ([AGENTS.md — Layout](file:///Users/p0is0n/GitHub/enzo/AGENTS.md)). Citation accuracy: verify path exists and line_start..line_end content contains the expected keyword/phrase — resolves invariant #2 deterministically without an LLM judge ([AGENTS.md — Invariants](file:///Users/p0is0n/GitHub/enzo/AGENTS.md)). No golden question set exists yet (~60-100 labeled questions needed), no harness code exists yet, and no CI gate for retrieval quality yet (threshold e.g. nDCG@10 ≥ 0.7, recall@10 ≥ 0.85) ([AGENTS.md — Build & test](file:///Users/p0is0n/GitHub/enzo/AGENTS.md)).

Abstain when there is no corroborating evidence: no keyword hit with full term coverage, no semantic hit ≥ floor (0.25), or top fused confidence is Low; answer only on Medium/High ([src/core/search/pipeline.rs confidence_for](file:///Users/p0is0n/GitHub/enzo/src/core/search/pipeline.rs); [AGENTS.md — Invariants](file:///Users/p0is0n/GitHub/enzo/AGENTS.md)). Penalty-aware evaluation: answer iff P(correct) ≥ k/(k+1); with k=4 that is an 80% confidence threshold ([Why RAGs Hallucinate: Penalty-Aware Evaluation](https://arxiv.org/html/2608.26385v1)). Correct Abstention Rate is the percentage of unanswerable questions on which the system acknowledges insufficient knowledge ([DeclineCraft: A RAG Abstention Benchmark](https://arxiv.org/pdf/2610.28340.pdf)). No NOT_ANSWERABLE classifier or query-type router exists yet; abstention is currently only "no hits → not_found" and Low-confidence hits still produce an answer ([A Three-Action Framework for Epistemically Calibrated QA](https://arxiv.org/html/2604.04565); [Microsoft: Confidence-Aware RAG](https://techcommunity.microsoft.com/blog/azuredevcommunityblog/confidence-aware-rag-teaching-your-ai-pipeline-to-acknowledge-uncertainty/4515061)). No cost/penalty parameter k exposed in config; abstention threshold is implicit in the Confidence enum, not tunable ([src/core/search/pipeline.rs confidence_for](file:///Users/p0is0n/GitHub/enzo/src/core/search/pipeline.rs)).

## Conclusion

Paper's release candidate should ship with a fully pure-Rust extraction stack and no generative polish. The extraction, multilingual, retrieval, hardening, and generation research converges on one disciplined default path: pure-Rust crates (lopdf, docx-rs, calamine, pptxboss-core, rbook, mailparse) for citations that resolve; multilingual-e5-small as the single default embedding model with script-based segmentation; RRF(k=60) and exact sqlite-vec KNN kept as-is; structure-aware chunking, SQL metadata filters, deterministic field extraction, and confidence-based abstention as the quality improvements; and signed artifacts, supply-chain gates, copyleft-free licensing, parser isolation, robustness, performance budgets, and an offline eval harness as RC1 blockers. Generative polish is explicitly deferred to post-RC, built first on user-supplied local servers, with Apple Foundation Models as a macOS-only bonus and OpenRouter as a strictly opt-in, heavily disclosed cloud path. What remains unknown — per-crate binary-size contributions, exact multilingual-e5-small safetensors download size, Candle loadability without sentence-transformers pooling, Windows Media OCR Rust bindings, placeholder detection per OS, and the golden question set — must be resolved during implementation but should not block RC1.
