# One setup verb buys three-platform parity

Paper can deliver identical install, discovery, indexing and integration behaviour on Windows, Linux and macOS, but not by making the three operating systems behave alike — they cannot. Parity comes from **one idempotent, network-free `paper setup` verb** that does nothing except *registration* (service unit, MCP configs, marker files), plus **a per-OS supervisor that owns the lifecycle** (launchd LaunchAgent, systemd `--user` unit, Windows logon Scheduled Task), plus **one daemon that owns all provisioning** (model download, first index, IPC). Everything else in this report is a consequence of that split. The install channels are unequal — only Homebrew, Scoop, npm and Chocolatey have a real post-install hook, and cargo-dist, `cargo install`, winget, GitHub Releases and Docker have none ([cargo-dist](https://axodotdev.github.io/cargo-dist/book/installers/shell.html), [winget-pkgs](https://github.com/microsoft/winget-pkgs)) — so the hook can never be the plan, only an accelerator. Discovery must come from `SHGetKnownFolderPath`, `user-dirs.dirs` and `NSFileManager`-equivalent paths, never from `$HOME/Documents` string joins, and must then be filtered for cloud placeholders, reparse points, bind mounts and TCC-protected folders. The macOS permission grant is a **code-signing problem**: an ad-hoc `cdhash` requirement cannot survive a rebuild, and a versioned install path breaks even correctly signed bundles ([claude-code #91854](https://github.com/anthropics/claude-code/issues/91854)). Model provisioning must be **embedder-first, index-on-embedder-ready, reranker-parallel**, with hash-verified resumable downloads, because the only thing worse than a 134 MB blocking download is a 1.13 GB one. And MCP registration is not one schema but five families across thirteen clients, so it must be a **text-preserving merge tool with a sidecar ownership record**, not a template string. The notes behind this report contain no Windows hardware verification and several explicitly unverified claims, flagged below rather than smoothed over.

## One setup verb absorbs thirteen unequal install channels

The single most consequential design decision is to stop treating installation as one event. **Registration work is small, local, synchronous and safe to repeat**; provisioning work is hundreds of megabytes, networked, minutes long, and unsafe to repeat. Every channel failure in this space comes from conflating them. `paper setup` should therefore mean *"make the system consistent with the intent to run Paper"* — create dirs, write the service unit, start the daemon, merge MCP configs — and should target **under ~150 ms with no network access**. The daemon it starts is the only component that downloads weights or builds an index.

The channel survey makes this non-negotiable. cargo-dist's installers are "thin wrappers" that fetch and unpack an archive, and the book states twice that they "cannot run any kind of custom install logic"; the only install-time knob is a static `install-success-msg` string, and both script installers deliberately "throw out all files except for the binary" ([shell installer](https://axodotdev.github.io/cargo-dist/book/installers/shell.html), [powershell installer](https://axodotdev.github.io/cargo-dist/book/installers/powershell.html), [issue #307](https://github.com/axodotdev/cargo-dist/issues/307)). Homebrew has moved post-install to a restricted declarative DSL — "`post_install_steps` … may only contain the supported step calls with literal arguments. It cannot call the wider formula DSL or arbitrary Ruby code" ([Formula Cookbook](https://docs.brew.sh/Formula-Cookbook)) — so "run the binary at install" is dead there, and the idiomatic answer for "run this once" is `caveats`. winget refuses script-based installers outright ([winget-pkgs README](https://github.com/microsoft/winget-pkgs)) and its validation runs installers silently, non-elevated, treating interactivity as a blocking failure ([ValidationFailureGuide](https://github.com/microsoft/winget-pkgs/blob/master/doc/ValidationFailureGuide.md)). `cargo install` still has no post-install hook at all ([cargo#11539](https://github.com/rust-lang/cargo/issues/11539)).

| Channel | Hook? | What it may safely do | Policy that bites | Verdict |
|---|---|---|---|---|
| `cargo install` | None | — | No hook exists ([cargo#11539](https://github.com/rust-lang/cargo/issues/11539)) | First run only |
| cargo-dist shell / PowerShell | None documented | Nothing inside the installer | "Cannot run any kind of custom install logic" ([book](https://axodotdev.github.io/cargo-dist/book/installers/shell.html)) | Wrapper script, or `install-success-msg` + first run |
| Homebrew formula | `post_install_steps` only | `mkdir_p`, `touch`, symlink | Literal args, sandboxed, no arbitrary Ruby ([cookbook](https://docs.brew.sh/Formula-Cookbook)) | `caveats`; never network |
| Scoop | `post_install` | `paper.exe setup --detach --no-service` | Arbitrary PowerShell, but no elevation assumption ([App Manifests](https://github.com/ScoopInstaller/Scoop/wiki/App-Manifests)) | Best Windows hook available; milliseconds only |
| npm | `postinstall` | fire-and-forget spawn, always `exit 0` | Output hidden since npm@7; failure aborts install unless swallowed ([npm scripts](https://docs.npmjs.com/cli/v10/using-npm/scripts)) | Use, never trust |
| winget | None | — | Script installers unsupported; silent + non-elevated validation | `zip`/`portable`; first run only |
| Chocolatey | `chocolateyInstall.ps1` | Arbitrary, elevated | Runs elevated (details unverified in these notes) | Skip — Paper is a no-admin product |
| GitHub Releases / source build | None | — | — | First run only |
| Docker | None at pull | Entrypoint | — | Bake models or mount `PAPER_HOME` |
| Claude Code plugin / `.mcpb` / MCP Registry | None; declarative | Registration only | MCP servers auto-start when enabled; lifecycle hooks were closed `not_planned` ([#48986](https://github.com/anthropics/claude-code/issues/48986)) | Nothing to hook; make `serve` non-blocking |

Two derived rules matter more than the table. First, **installers may only do work that is safe to do twice, safe to skip, and safe to fail**; service registration and marker files qualify, model downloads do not. Second, because `curl … | sh` feeds the script itself on stdin, any install-time hook must be non-interactive by construction, which conveniently also makes it safe under `irm | iex`, npm's hidden output, and CI. The strongest precedent for the verb itself is Tailscale: Scoop only extracts a zip, so Tailscale had to expose its own installer command to create its service ([Scoop Extras #13460](https://github.com/ScoopInstaller/Extras/issues/13460)). Paper's `paperscope` binary is already the only artifact every channel delivers, so it should be the installer.

Concretely, the command surface should collapse today's implicit behaviour into one explicit verb:

```text
paper setup [--detach] [--foreground] [--no-service] [--no-models]
            [--clients=claude,codex,...] [--status] [--json] [--force]
paper daemon-control {install,uninstall,start,stop,restart,status}
```

Phases belong in a journal under `$PAPER_HOME/setup/`, each a small atomic JSON record `{schema, binary_version, completed_at, artefact_digest?}`: `dirs`, `service`, `start`, `integrations` (keyed by binary version and config-schema version), then — daemon-only — `models` and `index`. A single "done" flag cannot express this: a binary upgrade must re-verify `service` (the `ExecStart` path may have moved) and may need `integrations`, but must never invalidate `models`. That is precisely the bug that makes every `brew upgrade` re-download 1.13 GB if the model directory embeds the binary version; Paper already pins model revisions plus per-file SHA-256, so the artefact key must stay `(name, sha256)`.

The concurrency design in `src/bootstrap.rs` today is the thing to replace, not extend. It uses `File::create_new` as a mutex with a **15-minute stale takeover**, and `SKIP_COMMANDS` does not include `serve`, so an editor opening five MCP sessions runs `ensure_service()` five times, serialised only by that lock. The takeover is racy (two processes can both observe staleness and both re-create), and `serve` must never take the setup lock at all: it should `try_lock`, log one line if held, and serve keyword-only results immediately. Kernel-owned advisory locks (`flock` / `LockFileEx`, via `fs4` or `fd-lock`) release on process death, which removes the staleness heuristic entirely. The first-run path then becomes: if disabled/portable/CI, return; if the journal is complete and the daemon is alive, return; else `try_acquire` and spawn `setup --foreground --quiet` detached, returning in milliseconds. Five concurrent `paper serve` plus one `setup --foreground` must yield exactly one provisioning run and five sub-100 ms serves — a test worth writing before the code.

## Three supervisors can share one IPC contract, but Windows needs a task, not a service

The parity target is **per login, not per boot**. launchd's `RunAtLoad` in `gui/<uid>` and systemd `--user`'s `default.target` both start with the user session; the Windows equivalent is a **Scheduled Task with an at-logon trigger and an interactive token** (`TASK_LOGON_INTERACTIVE_TOKEN`, `/it`, `/rl LIMITED`). An SCM service is disqualified twice over: it needs elevation, and since Vista services "cannot directly interact with a user" and all run in session 0 ([Interactive Services](https://learn.microsoft.com/en-us/windows/win32/services/interactive-services)). "Run whether user is logged on or not" is *more* than parity and unusable: the no-password variant is S4U and needs the batch-logon right, and both variants move the process out of the session where the user's profile, mapped drives and Explorer context live.

| Concern | macOS | Linux | Windows |
|---|---|---|---|
| Supervisor artefact | `~/Library/LaunchAgents/tools.kintsugi.paper.plist` | `~/.config/systemd/user/paper.service` | Task Scheduler task `Paper` (XML) |
| Start trigger | `RunAtLoad` | `WantedBy=default.target` | `LogonTrigger` for the user |
| Restart on crash | today `KeepAlive=false` — **no supervision** | `Restart=on-failure` | `RestartOnFailure` PT1M ×3 |
| Singleton | `first_pipe_instance` equivalent (bind) | same | `MultipleInstancesPolicy=IgnoreNew` **plus** pipe guard |
| Status query | `launchctl print gui/$UID/...` | `systemctl --user status` | `schtasks /query /tn Paper /xml` (locale-free) |
| Stop | `launchctl bootout` | `systemctl --user stop` | IPC `Shutdown`, `/end` as hammer |
| Uninstall | `bootout` + delete plist | disable + delete unit | `/end` then `/delete /f` |
| IPC transport | Unix socket + `getpeereid` | Unix socket + `SO_PEERCRED` | Named pipe `\\.\pipe\paper-<user-SID>` |
| Peer auth | UID equality | UID equality | DACL (owner+SYSTEM) **and** client-SID check |
| Visible console | n/a | n/a | Must be suppressed (`CREATE_NO_WINDOW`; see below) |
| Dies at logoff | yes | yes | yes (interactive-token task) |

The Windows row is the only one that requires new mechanism, and the notes are explicit that **no Windows hardware was available** for verification — every behavioural claim below needs a Windows 11 + Windows 10 22H2 pass before the design is treated as settled. What is documented: `schtasks` supports `/sc onlogon` and `/it` ("run only when the run-as user is logged on"), `/rl LIMITED` is the default, `/tr` "must not exceed 262 characters", and only tasks running as SYSTEM or another account require admin ([schtasks create](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/schtasks-create)). The supervisor properties `schtasks` flags cannot express — `RestartOnFailure`, `MultipleInstancesPolicy`, `ExecutionTimeLimit=PT0S`, `DisallowStartIfOnBatteries=false`, `StartWhenAvailable` — come from the task XML schema ([Task Scheduler Schema](https://learn.microsoft.com/en-us/windows/win32/taskschd/task-scheduler-schema)), which means Paper should add a pure `render_task_scheduler_xml(exe, sid) -> String` beside the existing pure `render_launchd_plist` and `render_systemd_unit` renderers in `src/cli/daemon.rs`, snapshot-test it on all three platforms, and register with `schtasks /create /tn Paper /xml <file> /f`. Field experience (unverified) says the XML must be **UTF-16LE with BOM**; `schtasks` rejects UTF-8.

The non-admin claim is the weakest link in the Windows design and is flagged accordingly: the documented cases requiring elevation are SYSTEM and other-account tasks, and practitioner sources confirm plain per-user logon tasks work without admin, but **no fetched Microsoft sentence says "a standard user may register a task that runs as themselves."** Treat it as high-confidence-but-not-officially-worded. The correct implementation therefore attempts registration, and on access-denied/policy failure degrades to a `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` value plus an immediate spawn, recording a new `ServiceState::Degraded` that `paper doctor` can explain — which finally makes the existing doc-comment in `bootstrap.rs` ("fall back to a detached daemon for this login session") true.

Transport choice is where Windows parity is won or lost. **Named pipes in byte mode with JSON-lines**, using `tokio::net::windows::named_pipe`, are the only transport that is first-class async on Windows, kernel-scoped (no filesystem artefact, hence no stale-socket cleanup), and ACL-able per user. Loopback TCP is rejected on threat-model grounds, not performance: any local process — and any web page via DNS rebinding — can reach `127.0.0.1`, and Ollama's unauthenticated `localhost:11434` produced CVE-2024-37032 ([NVD](https://nvd.nist.gov/vuln/detail/CVE-2024-37032)). The default pipe security descriptor is unacceptable as-is: with `lpSecurityAttributes = NULL` it grants "read access to members of the Everyone group and the anonymous account" ([Named Pipe Security and Access Rights](https://learn.microsoft.com/en-us/windows/win32/ipc/named-pipe-security-and-access-rights)). Paper needs an explicit DACL granting `GENERIC_ALL` to the user SID and SYSTEM with `PROTECTED_DACL_SECURITY_INFORMATION`, passed through `ServerOptions::create_with_security_attributes_raw`, plus a post-connect `GetNamedPipeClientProcessId` → `OpenProcessToken` → `TokenUser` SID comparison that replaces `peer_uid()` under `#[cfg(windows)]`. Use `first_pipe_instance(true)` as the singleton lock: "creation of any subsequent instances will fail with `PermissionDenied`", which is strictly better than the Unix "socket file exists — is it alive?" dance, and means the Windows code must **not** port the `remove_file(socket)` cleanup. Keep `PipeMode::Byte` — message mode yields `ERROR_MORE_DATA` when a line exceeds the read buffer and breaks `AsyncBufReadExt::lines()` ([ServerOptions](https://docs.rs/tokio/latest/tokio/net/windows/named_pipe/struct.ServerOptions.html)).

Two Windows-specific spawn hazards need explicit handling. First, a console-subsystem `paper.exe` launched by Task Scheduler allocates a console, so either accept a one-off flash at logon or ship a tiny GUI-subsystem shim (`#![windows_subsystem = "windows"]`, ~30 lines) whose only job is to spawn `paper daemon --foreground` with `CREATE_NO_WINDOW` and exit; do **not** flip the whole binary to the GUI subsystem, because that detaches stdout and breaks the CLI and the MCP stdio server. Whether Task Scheduler visibly flashes for a console action in *every* configuration is unverified — the shim is a hedge, not a confirmed necessity. Second, editors and IDEs commonly put children in a job object; `CREATE_BREAKAWAY_FROM_JOB` is fatal with `ERROR_ACCESS_DENIED` unless the parent's job set `JOB_OBJECT_LIMIT_BREAKAWAY_OK`, so the spawn must *attempt* it, retry without it on failure, and — because a job with `KILL_ON_JOB_CLOSE` defeats detachment entirely — rely on the registered task for durability rather than on the detached process ([Process Creation Flags](https://learn.microsoft.com/en-us/windows/win32/procthread/process-creation-flags)). On Unix the equivalent is the double fork (`fork` → `setsid` → `fork` → `chdir("/")` → redirect stdio → `exec`), because `setsid` fails with `EPERM` when the caller is already a process-group leader ([setsid(2)](https://man7.org/linux/man-pages/man2/setsid.2.html)).

Upgrades are the last piece of lifecycle. Models and the index live under `PAPER_HOME`, keyed by pinned revision and SHA-256, never under the binary's directory, so a binary upgrade cannot touch them. One location decision is worth fixing in the same pass: `Paths::new()` takes data from `dirs::cache_dir()` and `config.toml` from `dirs::config_dir()`, and on Windows the latter is the roaming profile ([dirs::config_dir](https://docs.rs/dirs/latest/dirs/fn.config_dir.html)), so machine-specific document roots would follow a roaming profile between machines. Config belongs beside the data under LocalAppData, with `PAPER_HOME` still authoritative for tests and portable installs. Registration state lives in the setup journal keyed by `binary_version`, so an upgrade re-runs only phases whose schema changed. On Windows, a running image can be renamed but not deleted or overwritten — a fact resting on community sources plus the `PendingFileRenameOperations` documentation, **not** a fetched Microsoft statement, so validate it on the runner before depending on it — which gives the sequence: verify the downloaded binary, write `paper.exe.new` on the same volume, IPC `Shutdown`, stop the task, rename current to `paper.exe.old-<version>`, rename new into place, `/run`, poll `daemon-control status --json` for the expected version, and sweep `.old` at next start ([MoveFileExW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw)). Defender can hold a share lock on the freshly written file for a few hundred milliseconds, so retry `MoveFileEx` 3–5 times with 100–500 ms backoff. The daemon should also compare its compiled version against the on-disk binary at start and exit "superseded" so the supervisor restarts the new one; note that launchd's current `KeepAlive=false` means that exit would leave nothing running, so the plist needs `KeepAlive { SuccessfulExit: false }` or the same bug ships.

## Discovery is an OS API call plus a distrust filter

Paper's current `discover_default_roots()` joins `dirs::home_dir()` with `Documents`, `Desktop` and `Downloads`. That is wrong on two of three platforms in ways users notice immediately: on Windows, OneDrive Known Folder Move relocates `Documents` and leaves the old `%USERPROFILE%\Documents` empty or stale; on Linux, the folder may be `~/Dokumente` or `/mnt/data/Docs`. The fix is to ask the OS and treat the answer as a *candidate*, not a fact.

| OS | Authoritative API | What it returns | What it cannot tell you |
|---|---|---|---|
| Windows | `SHGetKnownFolderPath(FOLDERID_Documents/Desktop/Downloads)` | Current, redirected path (incl. KFM); `hToken = NULL` means current user; no trailing backslash ([Known Folders](https://learn.microsoft.com/en-us/windows/win32/shell/known-folders)) | Whether the folder is cloud-backed, or which volume it sits on |
| Linux | `$XDG_*_DIR`, then `$XDG_CONFIG_HOME/user-dirs.dirs` (`XDG_DOCUMENTS_DIR` etc.) | The literal, localised path — possibly outside `$HOME`; `"$HOME"` means *disabled* ([user-dirs.dirs(5)](https://man.archlinux.org/man/user-dirs.dirs.5.en)) | Nothing; the file simply may not exist |
| macOS | `NSFileManager.urls(for:in:)` (`NSDocumentDirectory`, `NSDesktopDirectory`, `NSDownloadsDirectory`) | The OS answer, sandbox or not ([Apple](https://developer.apple.com/documentation/foundation/filemanager/urls(for:in:))) | TCC state; iCloud enrolment is an xattr, not a path |

`dirs` already calls `SHGetKnownFolderPath` on Windows and parses `user-dirs.dirs` on Linux, and on macOS hardcodes `$HOME/Documents` — which is byte-identical to what `NSFileManager` returns outside a sandbox ([dirs 7.0.0 mac.rs](https://docs.rs/crate/dirs/7.0.0/source/src/mac.rs)). So the minimal correct dependency set is `dirs` plus, on Windows only, `known-folders` for the IDs `dirs` does not expose (`LocalDocuments`, `OneDrive`, `PublicDocuments`) ([known-folders](https://docs.rs/known-folders/latest/known_folders/)). Adding `objc2` for `URLsForDirectory` is not worth it until Paper ships as a `.app`.

Volume enumeration is the part that decides whether "machines with many local disks" works. `GetLogicalDrives()` is insufficient because a data volume can be mounted at `C:\Data` with no letter; the correct Windows path is `FindFirstVolumeW` → `GetVolumePathNamesForVolumeNameW` → `GetDriveTypeW`, which is exactly what `sysinfo` does ([sysinfo windows/disk.rs](https://docs.rs/crate/sysinfo/0.33.1/source/src/windows/disk.rs), [GetDriveTypeW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getdrivetypew)). On Linux, parse `/proc/self/mountinfo`, not `/proc/mounts`: only mountinfo exposes the mount ID, parent ID, `major:minor`, the filesystem root and per-mount options, which are what bind-mount and btrfs-subvolume dedupe require ([proc_pid_mountinfo(5)](https://man7.org/linux/man-pages/man5/proc_pid_mountinfo.5.html)). On macOS, `getfsstat(2)` is the citable fallback while `mountedVolumeURLs` remains unverified here. Filter by filesystem type: allow `ext4/xfs/btrfs/zfs/vfat/exfat/ntfs3/apfs`, deny `proc/sysfs/tmpfs/cgroup/overlay/squashfs/erofs/autofs`, and put `nfs/cifs/sshfs/9p` and anything removable behind opt-in. `sysinfo` is fine for capacity but cannot do this precisely, because its Linux source is `/proc/mounts` and it exposes neither `root` nor per-mount options.

Distrust applies at three more layers. On Windows, cloud placeholders must be skipped by attribute, not by opening the file: `FILE_ATTRIBUTE_RECALL_ON_DATA_ACCESS`, `RECALL_ON_OPEN` and `OFFLINE` identify not-locally-present content, and `FindFirstFileExW(..., FIND_FIRST_EX_ON_DISK_ENTRIES_ONLY)` "limits the results to files that are physically on disk" ([File Attribute Constants](https://learn.microsoft.com/en-us/windows/win32/fileio/file-attribute-constants), [FindFirstFileExW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-findfirstfileexw)). Hashing hydrates a placeholder, so "skip or require `--include-cloud`" is the only safe default. Junctions and volume mount points (`IO_REPARSE_TAG_MOUNT_POINT`) are traversal boundaries, not directories to descend ([Mounted Folders](https://learn.microsoft.com/en-us/windows/win32/fileio/determining-whether-a-directory-is-a-volume-mount-point)). On macOS, Desktop & Documents sync keeps `~/Desktop` and `~/Documents` as real directories enrolled in the CloudDocs File Provider via the `com.apple.file-provider-domain-id` xattr, while the `Documents` entry *inside* iCloud Drive is a symlink back to `~/Documents` — so adding both roots double-indexes everything ([cver.net](https://cver.net/devlog/unify-mac-ios-downloads)). On Linux, a `user-dirs.dirs` value may legitimately point at `/mnt/data/Docs`, which should outrank the bare `/mnt/data` volume root because the user configured it.

| Rank | Candidate | Base |
|---|---|---|
| 1 | Explicit `--root` / config / MCP `add_root` | 1000 |
| 2 | `FOLDERID_Documents` / `XDG_DOCUMENTS_DIR` / `~/Documents` | 900 |
| 3 | Desktop | 800 |
| 4 | Downloads | 700 |
| 5 | Cloud containers (`FOLDERID_OneDrive`, `com~apple~CloudDocs`, `~/Library/CloudStorage/*`) | 600 |
| 6 | Other known folders (Pictures, Music, Videos, Public) | 400–500 |
| 7 | User home | 200 |
| 8 | Fixed volume root / mount point | 100 |
| 9 | Removable volume | 0 (opt-in) |
| 10 | Network volume | −100 (opt-in) |

Modifiers are cheap and metadata-only: `+40` exists and is a directory, `+30` readable, `−200` inside a system/tooling directory, `−150` volume root with no `Documents`/`Users`/`Desktop` child, `−300` macOS TCC-protected without consent, `−100` high cloud-only ratio (sampled, never recursively). Deduplicate by canonical path and ancestor relationship **before and after** scoring, by volume GUID on Windows (a volume mounted at both `D:\` and `C:\Data` appears twice), and by `(major:minor, root)` on Linux. The canonical `Candidate` record carries `kind`, `source`, `exists`, `readable: Option<bool>` (None = not probed, because on macOS a probe can trigger the consent dialog), `fs_kind`, `cloud`, `cloud_only_ratio`, `requires_consent` — and the ranking must stay **advisory**: mark ranks 1–5 as `default_selected` when they exist and are readable, and require an explicit opt-in for volume roots, removable media and network shares. A search tool that silently crawls `D:\` because it scored 100 will burn hours of I/O and lose the user's trust in one go.

Walking is the other half of scale. Keep `walkdir` (already a dependency), never follow links by default, set `same_file_system(true)` so a bind mount or junction cannot re-enter the tree, and enforce budgets — depth 12–16 for known folders and 3–4 for volume roots, 250k–1M entries per root, 50–100 MB per file, 60–300 s at startup with incremental continuation. Treat per-entry errors as non-fatal and map them to distinct diagnostics: `EPERM` on macOS means TCC, `EACCES` means POSIX; on Windows `ERROR_ACCESS_DENIED` means ACL/BitLocker/Controlled Folder Access and `ERROR_NOT_READY` means a locked volume. Persist per-root crawl state (last complete mtime, cursor, seen file IDs) so an interrupted multi-hour scan of a 4 TB disk resumes instead of restarting, and prefer **one worker per physical device**, not per root — parallel reads on one HDD thrash. The stable index key should be a file identity (volume serial + file index on Windows, inode/dev on Unix) rather than the display path, because paths change with drive letters, junctions and OneDrive redirection. Finally, watching cannot be trusted as the sole change detector: `ReadDirectoryChangesW` "will still return true, but the entire contents of the buffer are discarded" on overflow and tells you to enumerate the subtree, and `notify` itself warns that a large watch "may fail to receive all events" ([ReadDirectoryChangesW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-readdirectorychangesw), [notify](https://docs.rs/notify/latest/notify/)). Paper's existing five-minute tick is the reconciler — keep it, add an immediate stat-walk on any watcher error or watched-root removal, and skip reparse points and dehydrated files there too.

## The macOS grant survives only when identity and path both stop changing

TCC does not store "Paper is allowed". It stores a serialised code requirement (`csreq`) and, at each access, recomputes the caller's identity and asks whether it satisfies that requirement. For an ad-hoc or linker-signed binary the auto-generated designated requirement collapses to `cdhash H"…"`, so **every rebuild produces a new identity** and the old row becomes an orphan while the Privacy pane still shows the toggle on ([Nick Liu](https://nick-liu.com/posts/tcc-cdhash-trap/), [aidrivenlife](https://www.aidrivenlife.com/blog/01-adhoc-codesign-orphans-tcc)). That single fact explains the re-prompt loop, and it also explains the observed `DB Action:None`: tccd evaluated the request but neither applied nor wrote a decision, which is a symptom of an identity/attribution problem, not of the user's answer. Signing with any certificate changes the requirement to `identifier "…" and certificate leaf = H"…"`, which is stable across rebuilds; the Developer ID auto-generated form binds to the **Team ID (OU)**, so annual certificate renewal does not break it ([Santa TCC profile docs](https://northpole.dev/deployment/profile-tcc/)).

| Option | Durable grant | Survives rebuild | Survives upgrade | What the user sees |
|---|---|---|---|---|
| Developer ID + notarization, fixed path, stable `--identifier` | Yes | Yes | Yes, if path is unversioned and Team ID unchanged | One normal dialog; entry in Privacy & Security; no Gatekeeper warning |
| Developer ID, not notarized | Yes (TCC ignores notarization) | Yes | Yes | Same dialog, but Gatekeeper blocks the quarantine download |
| Self-signed cert, fixed `--identifier`, fixed path | Yes per multiple independent reports | Yes | Yes, until the cert is rotated or lost | Same dialog; Homebrew cask audit still unhappy |
| Apple Development cert | Technically yes | Yes | No — expires/re-provisions | Gatekeeper rejects on other machines |
| Signed `.app`, ad-hoc | No | No | No | Friendly name, silently stops matching after each build |
| Status quo: ad-hoc, linker-signed | No — `DB Action:None` suggests not even a row is written | No | No | Prompt on every launch; trust lost |

Two conclusions follow for the design doc. First, **the fix is identity before packaging**: sign every shipped binary with a stable identifier using either a Developer ID Application certificate (US$99/year, notarizable, required for a Homebrew cask) or a self-signed code-signing certificate with a fixed `--identifier` (free, yabai-style, cargo/curl/plugin channels only) — provided the 20-minute experiment in the notes confirms that macOS never demands a trust anchor for a self-signed leaf. That experiment is the single highest-value hour of work in this whole programme, because the self-signed claim, though corroborated by four independent reports plus the yabai/AeroSpace precedent, has **no primary Apple source**; and self-signed has three operational traps: lose the private key and every user's grant is orphaned forever, rotate the cert and the same happens, and any build on the user's own machine (`cargo install`) re-signs ad-hoc and silently undoes the grant ([yabai wiki](https://github.com/koekeishiya/yabai/wiki/Installing-yabai-(latest-release)#codesigning-yabai)).

Second, **the install path must never contain a version**. Claude Desktop's embedded engine, correctly signed by Anthropic and notarized, still failed with `DB Action:None` because its path was `…/claude-code/2.1.246/claude.app`; the reporter's diagnosis was "a path-stability problem, not a code-signing one" ([claude-code #91854](https://github.com/anthropics/claude-code/issues/91854)). A bare Mach-O at a versioned path accumulates one path-keyed (`client_type=1`) TCC identity and one orphaned row *per release* ([claude-code #87144](https://github.com/anthropics/claude-code/issues/87144)). This is why the Homebrew **formula** channel cannot deliver a durable grant at all — Homebrew builds the bottle itself and installs it under `Cellar/paper/<version>/`, so the artifact is Homebrew's ad-hoc signature, not Paper's ([Homebrew Security and Supply Chain](https://docs.brew.sh/Homebrew-Security-and-Supply-Chain)). If Paper supports `brew install`, the LaunchAgent must point at a Paper-managed, Paper-signed copy under a fixed path (for example `~/.local/share/paper/bin/paper`), never through the `bin/paper` symlink into the Cellar.

The verification tooling is not optional, because Apple documents none of this. `codesign -d -r- "$(command -v paper)"` must show `identifier` + `certificate leaf`, not `cdhash`; `codesign -dvvv --entitlements :-` shows what TCC sees; resolving the `command -v` symlink shows whether the real path is versioned; `sqlite3 "$HOME/Library/Application Support/com.apple.TCC/TCC.db" "select service, client, client_type, auth_value, csreq is not null from access where client like '%paper%'"` shows whether a row was actually written; and `log stream --info --debug --predicate 'subsystem == "com.apple.TCC"' | grep -i paper` shows the live decision ([TCC internals](https://eclecticlight.co/2026/04/08/privacy-files-folders-or-full-disk-access/)). Build a `paper doctor --tcc` that runs all four and prints a verdict; it turns the most expensive support ticket class into a self-service answer.

Full Disk Access is the documented fallback, not the default. It is `kTCCServiceSystemPolicyAllFiles`, stored in the **system** database, and it short-circuits the per-folder check — Oakley's logs show AllFiles being evaluated before `kTCCServiceSystemPolicyDocumentsFolder` ([Eclectic Light](https://eclecticlight.co/2026/04/08/privacy-files-folders-or-full-disk-access/)). It is the same csreq problem with a vastly broader blast radius: it grants read access to Mail, Messages, Safari history and every other protected location, which for a product whose pitch is "local-first, no telemetry" reads as malware behaviour. If it is used at all, grant it to a frozen, stably signed access broker and let the versioned indexer talk to that. Do not count on security-scoped bookmarks or `NSFileCoordinator`: the former is an App Sandbox mechanism that requires entitlements and an initial user selection, and the latter is about coordinated access, not authorization ([Apple](https://developer.apple.com/documentation/security/accessing-files-from-the-macos-app-sandbox)).

The attribution chain is the trap that will bite the plugin channel. TCC evaluates the **responsible process**, and when an Electron editor spawns a tool, tccd names the editor as responsible even though `binary_path` points at the tool ([Orca #12971](https://github.com/stablyai/orca/issues/12971), [block/buzz #2783](https://github.com/block/buzz/issues/2783)). Consequences: the prompt says the *editor* wants your Documents, Paper never appears in Privacy & Security, and a denial affects every tool that editor spawns. Only `responsibility_spawnattrs_setdisclaim()` at `posix_spawn` time escapes the inheritance, and that is a private API used by Terminal, iTerm2 and Homebrew ([Homebrew](https://docs.brew.sh/Homebrew-Security-and-Supply-Chain), [steipete](https://steipete.me/posts/2025/applescript-cli-macos-complete-guide)). Therefore the editor plugin must **install and register the LaunchAgent and let launchd own the process**, never run the indexer as its child. That decision also fixes the "five MCP sessions" problem and the "TCC prompt at login before WindowServer exists" risk: a LaunchAgent firing before the GUI session can get no dialog at all (unverified but plausible), so first-run consent should be deferred to the first user-visible action rather than attempted at boot.

## The embedder gates indexing; nothing else should gate anything

The requested ordering — embedder download starts immediately after install, indexing begins the moment the embedder is usable, reranker downloads in parallel — is the right shape, and it is also the only shape that does not make a first-run user wait on the wrong thing. The numbers justify it: **134 MB** embedder, **1.13 GB** reranker, **488 MB** optional multilingual embedder in this repo's `dist-workspace.toml` (note that one research note calls the 487 MB artifact "the reranker"; the repo says it is the multilingual E5 embedder, so use `dist-workspace.toml` as truth). A full vector backfill of 100k chunks costs **15 minutes to 1.5 hours of CPU** depending on hardware, from measured embedding throughput of 112 texts/s batched on an M1 Ultra down to ~35 texts/s single-text ([build.labs](https://pushkarkumar-dev.github.io/system-design-labs/embedding-pipeline), [Treeru](https://treeru.com/en/blog/cpu-embedding-benchmark-tool)). Making a search user wait for that before *any* result is indefensible when FTS5 over the same corpus answers in seconds.

So index text immediately, embed asynchronously, and gate only the semantic tier. The clean mechanism is a side table, not a nullable column on `chunks` (which is the FTS5 external-content table; churning it would fire triggers and pollute the index):

```sql
CREATE TABLE chunk_embedding (
  chunk_id  INTEGER PRIMARY KEY REFERENCES chunks(id) ON DELETE CASCADE,
  model_key TEXT NOT NULL,          -- 'bge-small-en-v1.5@sha256:...:384'
  state     TEXT NOT NULL,          -- 'pending' | 'ready' | 'failed'
  attempts  INTEGER NOT NULL DEFAULT 0,
  updated_at INTEGER NOT NULL
);
CREATE INDEX chunk_embedding_pending ON chunk_embedding(state) WHERE state = 'pending';
```

Insert the `pending` row in the *same transaction* as the chunk, so a crash can never leave an unembedded chunk with no marker. The embedder worker selects 512 pending rows, embeds, writes `chunks_vec` and flips state in one transaction. Because `model_key` embeds the weights hash, a model upgrade flips every row back to `pending` with one `UPDATE`. Search keeps tier0 always, joins tier1 against ready rows only, and returns `{"degraded":["semantic"],"pending_chunks":N}`; exit code stays `0` when tier0 found something and becomes `3` only when `--semantic` was explicit — preserving the project's existing contract. Triggering is a `watch::Receiver<ArtifactState>` the provisioner exposes: the indexer awaits `embedder == Ready`, then starts. No polling loop, no blocking startup.

The downloader itself should not be `hf-hub`. It is a good metadata and cache client, but its single-file path does a plain `GET`, truncates `<blob>.<etag>.incomplete` with `File::create`, and **never sends a `Range` header** — so an interrupted download restarts at byte 0 — and it never hashes the bytes it wrote ([download.rs](https://raw.githubusercontent.com/huggingface/hf-hub/main/hf-hub/src/repository/download.rs)). That silently violates Paper's "every model file is hash-pinned" invariant. A thin `reqwest` + `sha2` downloader is the correct choice, taking the cheapest correctness win from llama.cpp (a `.etag` sidecar, so "is this partial still the same object?" is a string comparison), Python's rule that any successful byte read resets the retry counter, and Ollama's 30 s stall detector ([llama.cpp download.cpp](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/common/download.cpp), [huggingface_hub](https://raw.githubusercontent.com/huggingface/huggingface_hub/main/src/huggingface_hub/file_download.py), [Ollama](https://raw.githubusercontent.com/ollama/ollama/main/server/download.go)).

| Tool | Resume | Integrity | Parallelism | Lesson for Paper |
|---|---|---|---|---|
| Ollama | 16 parts, JSON part files, sparse file | digest names, no end-of-download hash | 16 goroutines, 30 s stall abort | take stall detection, not 16 connections |
| llama.cpp | append to `.downloadInProgress` + `.etag` | ETag equality + length | one stream/file, files parallel | take the sidecar |
| `huggingface_hub` | `Range` + 5 retries, resets on progress | size vs expected | thread_map across files | take the retry-reset rule |
| `hf-hub` (Rust) | **none** | none | `buffer_unordered(8)` | do not use for downloads |

Mechanics that must be right: one `.part` plus a `.part.json` sidecar per artifact holding `{url, etag, last_modified, total, sha256, updated_at}`; resume with `Range` **and** `If-Range`, because a non-matching validator returns the full resource with `200 OK` and the client must then rewind and truncate rather than append ([MDN: If-Range](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/If-Range)); treat `416` and `200` on a resume as "partial is complete or garbage" — hash it, promote if it matches, otherwise delete; never trust a journalled offset, use `min(journal_offset, file_len)`; `fsync` the `.part`, rename, then `fsync` the directory; and preflight `sum(remaining) * 1.10 + 128 MiB` against `fs4::available_space` on the destination filesystem, failing with exit code 2 (not 3) and the shortfall in MiB. Handle `ENOSPC` as terminal for that artifact. Always send `Accept-Encoding: identity`, since a compressed `Content-Length` invalidates every offset. And do `HEAD` on the resolve URL, keep `X-Linked-Etag`/`X-Linked-Size`/`Accept-Ranges`/`Location`, then send resumed `GET`s to the CDN host directly; on `403` from an expired signed URL, re-resolve and keep the `.part` because the object is content-addressed.

Concurrency should be boring and bounded. A global `Semaphore(8)` for HTTP, `Semaphore(3)` for whole artifacts and up to 4 range connections per artifact gives a worst case of 12 sockets and a typical 4–8; part count `clamp(ceil(size / 32 MiB), 1, 8)` means 5 parts for the embedder and 8 for the reranker. Give the embedder priority for the first ten seconds so the gating artifact is not competing with a 1.13 GB download for sockets. Multi-connection gains are overstated on slow links: measurements show 1 connection at 2.4–17.4 MiB/s, 6 at 6.8–24.0, 16 at 19.2–27.3, with the author's conclusion that "extra connections buy consistency, not headroom" ([Kinburg/ModelDL](https://github.com/Kinburg/ModelDL)). Start at 2 and add only while per-connection throughput exceeds ~1 MiB/s and the file is >64 MiB. Do not use `multipart/byteranges`; one range per request is the only reliably parseable form ([huggingface_hub #2248](https://github.com/huggingface/huggingface_hub/issues/2248)). A ~40-line token bucket is better than reducing concurrency for a background provisioner that must not ruin a video call.

State and observability should be a document, not an IPC channel. `$PAPER_HOME/models/state.json` (atomic replace, `flock` exclusive for the single writer) plus `state.jsonl` transitions plus per-artifact `<sha256>/file`, `.part`, `.part.json`, `.lock` gives crash safety where the filesystem is truth and the JSON is a *view* reconciled at startup. `Absent → Queued → Downloading{offset, etag, total} → Verifying → Ready`, with `Paused` after process death, `Failed{Checksum}` terminal for the session, and `Ready` re-checked by size and mtime with a full hash only on suspicion. Progress fields (`bytes_done`, `bytes_total`, `rate_bps`, `eta_s`, `attempts`, `last_error`, `next_retry_at`) written at ≤4 Hz and always on transitions. The CLI and MCP server read the same file; MCP gets a `models_status` tool plus a compact `models` object in search responses, and "not ready" is never an error. Offline is a first-class state: `PAPER_OFFLINE=1` skips the network, resolves from state/disk, sets `Missing{offline}` when absent, and **never deletes resumable bytes**. Hostile networks need `rustls` with native roots (shipping `webpki-roots` only breaks every corporate MITM laptop), `PAPER_MODEL_ENDPOINT` or `HF_ENDPOINT` mirroring, and a diagnostic that distinguishes "cannot reach `huggingface.co`" from "reached the Hub but `us.aws.cdn.hf.co` timed out" — HF publishes its CDN host list at `https://huggingface.co/.well-known/meta.json` and notes that a mid-download read timeout "usually means … a storage or CDN host is blocked" ([HF downloading models](https://huggingface.co/docs/hub/en/models-downloading)).

## Registration is a merge problem dressed as thirteen config dialects

The stdio transport has no negotiation for "how do I start you": the client spawns `command` with `args` and a merged environment, then exchanges newline-delimited JSON-RPC on stdin/stdout, with stderr reserved for logs and messages forbidden from containing embedded newlines ([MCP spec](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/stdio)). Every client therefore invents a schema, and there are **seven distinct shapes**: an `mcpServers` object (Claude Code/Desktop, Cursor, Windsurf, Cline, Gemini, Antigravity), a `servers` object (VS Code editor-managed), `context_servers` (Zed), `mcp.servers` with `command` as an **array** and `environment` not `env` (OpenCode V2), `[mcp_servers.*]` TOML (Codex), an `mcp_servers` YAML mapping (Hermes), and a YAML **array** keyed by `name` (Continue). One canonical entry cannot be a template string; it needs one serialiser per format and one adapter per client.

| Client | macOS | Linux | Windows | Format | Servers key |
|---|---|---|---|---|---|
| Claude Code | `~/.claude.json`, `<proj>/.mcp.json` | same | `%USERPROFILE%\.claude.json` | JSON | `mcpServers` |
| Claude Desktop | `~/Library/Application Support/Claude/claude_desktop_config.json` | `$XDG_CONFIG_HOME/Claude/…` else `~/.config/Claude/…` | `%APPDATA%\Claude\claude_desktop_config.json` | JSON | `mcpServers` |
| OpenCode | `~/.config/opencode/opencode.json[c]` | same | `%USERPROFILE%\.config\opencode\opencode.json` | JSON/JSONC | `mcp.servers` (V2) / `mcp` (V1) |
| Codex CLI | `~/.codex/config.toml` | same | `%USERPROFILE%\.codex\config.toml` | TOML | `[mcp_servers.<name>]` |
| Cursor | `~/.cursor/mcp.json` | same | `%USERPROFILE%\.cursor\mcp.json` | JSON | `mcpServers` |
| Windsurf | `~/.codeium/windsurf/mcp_config.json` | same | `%USERPROFILE%\.codeium\windsurf\mcp_config.json` | JSON | `mcpServers` |
| VS Code | `~/Library/Application Support/Code/User/mcp.json` (editor), `~/.copilot/mcp-config.json` (native) | `~/.config/Code/User/mcp.json` | `%APPDATA%\Code\User\mcp.json` | JSON(C) | `servers` / `mcpServers` |
| Zed | `~/.config/zed/settings.json` | same | `%APPDATA%\Zed\settings.json` | JSONC | `context_servers` |
| Cline | `~/.cline/data/settings/cline_mcp_settings.json`; VS Code `globalStorage/saoudrizwan.claude-dev/settings/…` | `~/.config/Code/User/globalStorage/…` | `%APPDATA%\Code\User\globalStorage\…` | JSON | `mcpServers` |
| Continue | `~/.continue/config.yaml` | same | `%USERPROFILE%\.continue\config.yaml` | YAML | `mcpServers` (**array**) |
| Gemini CLI | `~/.gemini/settings.json` | same | `%USERPROFILE%\.gemini\settings.json` | JSON | `mcpServers` |
| Hermes | `~/.hermes/config.yaml` | same | `%USERPROFILE%\.hermes\config.yaml` | YAML | `mcp_servers` (mapping) |
| Antigravity | `~/.gemini/config/mcp_config.json` | same | `%USERPROFILE%\.gemini\config\mcp_config.json` | JSON | `mcpServers` |

Three details in that table will otherwise cost days. **OpenCode V2** puts servers under `mcp.servers`, uses `command` as an executable-plus-args array, `environment` instead of `env`, `disabled` instead of V1's `enabled`, and `{env:NAME}` substitution rather than `$NAME` — a shared generator that emits `${VAR}` breaks here ([OpenCode MCP](https://opencode.ai/docs/mcp-servers.md)). **Codex** defaults `startup_timeout_sec` to 10 s, which a cold Paper index can exceed, and its own CLI "rewrites every `[mcp_servers.*]` entry, silently dropping comments and unknown keys" ([#45432](https://github.com/openai/codex/issues/45432)) — so a text-preserving TOML append is strictly safer than the vendor CLI. **Gemini**'s `MCPServerConfig` sets `additionalProperties: false`, so an installer marker key inside the entry invalidates the server; ownership must live out of band ([settingsSchema.ts](https://github.com/google-gemini/gemini-cli/blob/ce84b3cb/packages/cli/src/config/settingsSchema.ts)).

Detection must be tiered, because config-file existence — the primitive used by Wolfram's shipping multi-client installer — under-detects first-run clients and over-detects stale uninstalls ([AgentTools mcp-clients.md](https://github.com/WolframResearch/AgentTools/blob/main/docs/mcp-clients.md)). In descending confidence: explicit `--clients`/`--no-client`; a binary probe on `PATH` (`which claude`, `codex`, `opencode`, `gemini`, `hermes`, `cline`, `cn`, `zed`, `cursor`, `windsurf`, respecting `PATHEXT`); a macOS app bundle in `/Applications` or `~/Applications`; a vendor data directory (`~/.claude`, `~/.codex`, `~/.cursor`, `~/.config/opencode`, `~/.continue`, `~/.gemini`, `~/.codeium`, `~/.cline`, `~/.hermes`, `~/.copilot`); and only then the config file. Relocatable homes must be honoured or detection lies: `CLAUDE_CONFIG_DIR`, `CODEX_HOME`, `COPILOT_HOME`, `CLINE_MCP_SETTINGS_PATH`/`CLINE_DIR`, `XDG_CONFIG_HOME`, and Paper's own `PAPER_HOME`. And the hard rule: **never `mkdir -p` a vendor's config directory**. If `~/.continue` does not exist, the user does not use Continue, and creating it produces a ghost that every future run re-detects. Creating the *file* inside an existing directory is fine (`~/.codex/config.toml`, `~/.cursor/mcp.json`).

The merge algorithm is where correctness lives, and it is the same for every client: resolve the path; skip if detection fails; warn (do not block) if the app is running; read the file; back it up as `<file>.paper-bak-<iso8601>`; parse **preserving** comments and formatting (a CST — `taplo` for TOML, a JSONC-aware parser for JSONC — never a DOM round-trip); look up `paper` by key; no-op if normalized-equal; conflict unless `--force`; otherwise append last and write atomically via temp-in-same-directory → `fsync` → rename → `fsync(dir)`; then record `{client, path, key, sha256(entry), installed_at, installer_version}` in `$PAPER_HOME/clients.json`. Lock a sibling `<file>.paper.lock`, never the config file itself, because Windows cannot rename over a file another process holds open and some clients keep their config open for reading. Comparing entries should normalize on `{basename(command), args, env-subset}` so a user who moved Paper to `/usr/local/bin/paper` is reported as a *modification* and left alone, not treated as "already current" or as a hard conflict.

Vendor CLIs are the exception, not the rule. Use them only when the CLI is documented as additive, the file is application state, and the app is not running: Claude Code (`claude mcp add --scope user`, which prints `File modified:`), Cline (`cline mcp add … --yes`), and Gemini (`gemini mcp add -s user -t stdio`, noting the default scope is **project**, the opposite of Claude Code). Do not use Codex's (destroys comments), `code --add-mcp` (writes the deprecated editor-managed surface slated for removal in February 2027), or OpenCode's (no `remove` at all) ([VS Code MCP reference, 2026-11-18](https://code.visualstudio.com/docs/agents/reference/mcp-configuration)). The hybrid that is actually correct: try the CLI, then re-read and verify that (i) our entry exists, (ii) every pre-existing entry still exists, (iii) the comment count did not drop; on any failure restore the backup and fall back to a text merge.

| Client | Direct write | Real risk | Mitigation |
|---|---|---|---|
| Claude Code | Supported but discouraged | `~/.claude.json` is a large live state file | Prefer CLI; never write while `claude` runs |
| Claude Desktop | Supported | Extensions/admin policy override; restart required | Also ship `.mcpb`; say "quit fully" |
| OpenCode | Supported | V1/V2 key path; JSONC comments | Detect version; preserve comments |
| Codex | Supported | Vendor CLI destroys comments; 10 s startup default | Append TOML; raise `startup_timeout_sec` |
| Cursor | Undocumented, universal | Global file reported unreliable; Windows path bug | Write global; verify by re-read |
| Windsurf | Undocumented | Two/three conflicting current paths | Write only an existing path; never create `~/.config/devin` |
| VS Code | Supported | Deprecated surface removal Feb 2027; two schemas | Native `mcpServers` by default |
| Zed | Undocumented in effect | JSONC; two competing schemas | Flat `command` + `args` only |
| Cline | Supported | CLI vs extension paths diverge; `autoApprove` footgun | Offer both; write `autoApprove: []`, never `["*"]` |
| Continue | Supported | Malformed/missing top-level keys silently disable **all** MCP | Insert only; validate after write |
| Gemini CLI | Supported | Consumer deprecation → Antigravity; strict schema | No marker keys; only if `~/.gemini` exists |
| Hermes | Supported | YAML; only presets documented for its CLI | Append mapping key; validate by parse |
| Antigravity | Undocumented (UI is documented) | Cloud sync overwrite, macOS `$PATH`, launch caching | Absolute command path; full restart; idempotent re-run |

Two cross-cutting rules. **Absolute `command` paths are mandatory**: three independent failure reports — Antigravity's GUI not inheriting the login shell `$PATH`, Cursor's Windows path bugs, macOS GUI apps not inheriting shell PATH — all reduce to "the client may not have your environment". And **do not emit keys the client did not document**: `cwd` is fatal in Gemini and dropped in Codex, and Paper should omit it anyway because it indexes configured roots, not the working directory. On Windows, serialise with a real JSON writer (backslashes become `\\` automatically), prefer `%LOCALAPPDATA%\Programs\Paper\paper.exe` over `C:\Program Files\…` (no spaces, no admin, no 8.3 short-path workaround for clients that shell-invoke), and include the `.exe` suffix.

Uninstall must be keyed on the recorded entry, not on the name: delete one object key in JSON/JSONC, one table **plus its sub-tables** in TOML (`[mcp_servers.paper]` and `[mcp_servers.paper.env]`), one array element in Continue, one mapping key in Hermes. Refuse if the recorded hash no longer matches — the user edited it, so it is theirs — and print the diff with `--force` required. Delete a file only if Paper created it, it now contains an empty server container, and no other top-level keys exist; otherwise leave `{"mcpServers": {}}` in place. Never "restore the backup" as part of uninstall; a user may have edited the file since. Run uninstall **before** binary removal, and have `paper doctor` flag registered paths that no longer exist — stale entries pointing at a deleted binary are the most common "broken MCP server" report.

## Failure modes that will otherwise ship

These are the ones with sourced mechanisms and a concrete guard, ordered roughly by cost of getting them wrong. The through-line is that each one looks like a small local decision and is actually an architectural constraint.

| Failure | Mechanism | Guard |
|---|---|---|
| 1.13 GB re-download on every upgrade | Model directory embeds binary version | Key artefacts by `(name, sha256)`; verify `service` path on upgrade, never `models` |
| Grant dies after every rebuild | Ad-hoc signature ⇒ `cdhash` requirement | Stable identifier + cert; assert `codesign -d -r-` shows `identifier`+`certificate leaf` in CI |
| Grant dies after every upgrade | Versioned install path (`Cellar/…/2.1.246/…`) | Unversioned path or a Paper-managed signed copy; LaunchAgent points at the resolved path |
| `brew upgrade` leaves a dead daemon | `KeepAlive=false` and/or stale `ExecStart` | `KeepAlive{SuccessfulExit:false}`, restart-on-failure, re-verify `ExecStart` on every setup |
| Editor hangs on first launch | `serve` runs service install inline / blocks on lock | `try_lock`, log one line, serve keyword-only; never network I/O on the foreground path |
| Five sessions, five provisioning runs | Racy `create_new` + 15-min stale takeover | Kernel locks (`flock`/`LockFileEx`); phase journal |
| Stale MCP entry after uninstall | Entry deleted by name, or binary removed first | Hash-keyed removal; uninstall before binary removal |
| User's comments silently deleted | Codex CLI / DOM round-trip on JSONC/TOML | CST-preserving append; verify comment count after CLI use |
| Endless re-prompt on macOS from an editor | TCC attributes the *editor* as responsible | Plugin installs the LaunchAgent; launchd owns the process |
| OneDrive tree gets hydrated by indexing | Opening/hashing a placeholder fetches bytes | Attribute check + `FIND_FIRST_EX_ON_DISK_ENTRIES_ONLY`; opt-in for cloud-only |
| Watcher silently misses changes | `ReadDirectoryChangesW` overflow returns success | Five-minute stat-walk reconciler + rescan on watcher error or root removal |
| Local API reachable by any process | Loopback TCP, no peer auth | Named pipe with owner+SYSTEM DACL and client-SID check |
| Install blocked on Windows | Unsigned persistence+updater shape triggers Defender/SmartScreen | Authenticode via a consistent publisher identity; one persistence mechanism; no `%TEMP%` staging |

The signing economics deserve one paragraph because they set the schedule. SmartScreen reputation attaches to the publisher identity, and "reputation cannot transfer from previous versions unless both were signed using the same publisher identity"; self-signed is documented as behaving "the same as no signature", and since 2024 **EV certificates no longer bypass SmartScreen** ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation)). The realistic options for an individual are Azure Artifact Signing at ~US$9.99/month (identity validation required; individuals limited to the US and Canada), an OV certificate at US$150–300/year with a mandatory hardware token, or SignPath Foundation for open source ([code signing options](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/code-signing-options)). Expect warnings for the first weeks regardless, submit false positives after each release, and pick one identity and keep it for years — rotating the certificate resets reputation, which is the opposite of the macOS self-signed trade-off where rotation only breaks local grants. Microsoft now also states that an app registering a packaged MCP server for Windows agents "must be signed with a certificate that is part of the Microsoft Trusted Root Program", which makes signing a prerequisite for the Windows agent-integration story rather than a nice-to-have.

Linux needs no signing for any of this, and that is not a gap to fill: there is no Gatekeeper/TCC equivalent, confinement comes from systemd, and no mainstream channel requires the upstream binary to be signed ([Flatpak](https://flatpak-testing.readthedocs.io/en/latest/distributing-applications.html), [Snap](https://wiki.archlinux.org/title/Snap)). The effort belongs in a hardened unit instead: `ProtectSystem=strict`, `ProtectHome=read-only` with `ReadOnlyPaths=%h/Documents %h/Downloads %h/Desktop`, `NoNewPrivileges=yes`, `PrivateTmp=yes`, `RestrictAddressFamilies=AF_UNIX`, audited with `systemd-analyze security` ([systemd.exec](https://www.freedesktop.org/software/systemd/man/latest/systemd.exec.html)). Note the documented caveat that unprivileged per-user services cannot use every namespace option, so verify each directive actually applies rather than assuming the hardening landed.

## Conclusion

The tempting reading of this brief is "five features, three platforms, fifteen combinations" — a matrix to fill in. The notes support a simpler and more demanding conclusion: there are **two lifecycles**, and almost every failure in the sources is a lifecycle being crossed. Registration is milliseconds and must be idempotent, skippable and failure-tolerant; provisioning is hundreds of megabytes and must be owned by exactly one long-lived process with kernel locks and a hash-verified journal. A `paper setup` that does both is a worse design than a `paper setup` that does neither, and the current `bootstrap.rs` — service install inline on the first ordinary command, lock held across it, `serve` not exempt — is precisely the shape that makes an editor appear to hang. Fix the split first; the per-OS tables then become mechanical.

The second conclusion is that two decisions are effectively irreversible and should be made before any code is written. The macOS grant is decided by **code identity plus install path**, and neither can be retrofitted: if Paper ships ad-hoc from a versioned directory, every user accumulates orphaned TCC rows and the product earns a reputation for re-prompting, and no amount of `paper doctor` output repairs it. The Windows trust story is decided by **one publisher identity held for years**, because reputation is per-certificate and rotation resets it — and signing is now also a prerequisite for registering an MCP server with Windows agents. Everything else here can be iterated; those two cannot, which is why the 20-minute self-signed-versus-Developer-ID experiment and the certificate purchase belong before the implementation section, not after it. And treat the Windows half of this report as a design from documentation and community evidence, not from a machine: console flash, non-admin task registration, logoff termination, rename-while-running, `schtasks`' UTF-16 requirement and cross-account task visibility are all flagged unverified, as are the self-signed TCC claim and Windsurf's and Zed's current config shapes. One day of verification on real hardware is cheaper than shipping a supervisor that never starts.
