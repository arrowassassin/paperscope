# Optimizing SQLite Document Search with Compression and Deduplication

The most efficient storage algorithm for SQLite-based document search combines **ZSTD level 3 with per-content-type dictionaries for text**, **int8 scalar quantization with asymmetric distance computation for vectors**, and **FastCDC v2020 content-defined chunking with BLAKE3 hashing for deduplication**. This trio reduces text storage 3–5× and vector storage 4× while maintaining sub-100 ms query latency and exact citation resolution. For datasets exceeding 100k vectors, adding a binary quantization column with sqlite-vec's rescore index yields 6× faster search at 98.8% recall.

## ZSTD dictionary compression dominates text storage

For document chunks of 200–400 words (≈1–2 KB), ZSTD at compression level 3 achieves a 2.9× ratio with 510 MB/s compression and 1.5 GB/s decompression on the Silesia corpus ([Zstd GitHub benchmarks](https://github.com/facebook/zstd)). LZ4 decompresses faster (~4 GB/s) but only reaches 2.1× ratio. Brotli's 3.8× ratio comes at 100 MB/s compression — too slow for real-time indexing. The decisive advantage emerges with dictionary compression: training a ~100 KB dictionary on representative chunks of the same content type (PDF text, HTML, Markdown, code, email) improves ratio from ~4× to ~11× on structured data while doubling decompression speed on 1 KB blocks ([Zstd issue #4175](https://github.com/facebook/zstd/issues/4175)). ZSTD's "short cache" optimization adds 5–30% compression speedup for inputs under 8 KB at levels 1–2 ([Zstd PR #3152](https://github.com/facebook/zstd/pull/3152)). In Rust, the `rust-zstd` crate provides pure-Rust, byte-for-byte compatibility with libzstd 1.5.7 and full dictionary support without C dependencies ([crates.io/rust-zstd](https://crates.io/crates/rust-zstd)).

The practical architecture stores uncompressed text in FTS5 for tokenization while keeping a ZSTD-compressed copy in the `chunks` table. Since SQLite lacks native blob compression, application-level compression before insert is mandatory. For chunks under 500 bytes, ZSTD's "magicless frames" avoid the 4-byte frame overhead ([Zstd issue #3722](https://github.com/facebook/zstd/issues/3722)). At query time, a reused `Decompressor` with the dictionary hydrates top-K chunks in sub-millisecond latency — well within the 100 ms budget.

## int8 scalar quantization is the vector sweet spot

Paper's 384-dimension float32 vectors (1.5 KB each) compress 4× to 384 bytes with int8 scalar quantization while preserving 97–99% recall@10 via asymmetric distance computation (ADC), reaching 100% with float32 rescoring of the top-100 candidates ([CST Solutions](https://cstsolution.com/blog/quantising-embeddings)). Binary quantization achieves 32× compression (48 bytes) but recall drops to 85–92%; oversampling 4–8× with rescoring recovers to 95–99% ([Weaviate](https://weaviate.io/blog/binary-quantization), [MongoDB](https://www.mongodb.com/company/blog/product-release-announcements/binary-quantization-rescoring-96-less-memory-faster-search)). Product quantization offers 8–192× depending on subspace count but requires k-means training per subspace and complex ADC lookup tables — overkill below ~500k vectors.

sqlite-vec natively supports `int8[384]` and `bit[384]` column types alongside `float[384]`, storing vectors as packed BLOBs in shadow tables ([sqlite-vec.c](https://github.com/asg017/sqlite-vec/blob/main/sqlite-vec.c)). The new rescore index (PR #276) automates coarse-to-fine search: on 1M NYT headlines (mxbai-embed-large-v1, 384 dims), int8 with oversample=2 runs 2.6× faster at 100% recall; binary with oversample=8 runs 5.8× faster at 98.8% recall ([PR #276](https://github.com/asg017/sqlite-vec/pull/276)). Enabling `PRAGMA mmap_size=1073741824` cuts I/O overhead 25 ms at 50k vectors ([DEV Community](https://dev.to/arinaymay/37500-reads-per-search-what-memory-mapping-fixed-in-sqlite-vec-and-what-it-couldnt-256b)). The `vq` crate provides SIMD-accelerated `ScalarQuantizer`, `BinaryQuantizer`, and `ProductQuantizer` behind a unified `Quantizer` trait, all pure Rust ([docs.rs/vq](https://docs.rs/vq/latest/vq/)).

## FastCDC v2020 with BLAKE3 enables cross-document deduplication

Content-defined chunking (CDC) is essential for document corpora where edits shift content: fixed-size chunking destroys deduplication on every insertion, while CDC boundaries track content patterns so only local chunks change ([Restic Foundation CDC blog](https://restic.net/blog/2015-09-12/restic-foundation1-cdc)). FastCDC v2020 is the state of the art — ~10× faster than Rabin-based CDC with nearly identical deduplication ratios, using Gear hashing (single left-shift + table lookup per byte) and normalized chunking with dual masks to produce tight size distributions ([USENIX ATC 2016](https://www.usenix.org/conference/atc16/technical-sessions/presentation/xia), [fastcdc crate docs](https://docs.rs/fastcdc)). The `fastcdc` crate (200+ stars, pure Rust, deterministic) and `blake3` (SIMD, parallelizable, faster than SHA-256) form the minimal stack ([crates.io/blake3](https://crates.io/crates/blake3)).

Schema changes are minimal: add `hash TEXT UNIQUE NOT NULL` (BLAKE3 hex) and `ref_count INTEGER DEFAULT 1` to the `chunks` table, with a unique index on `hash`. Ingestion uses `INSERT OR IGNORE` followed by `UPDATE ref_count = ref_count + 1 WHERE hash = ?` — atomic in SQLite's single-writer CLI model. Deduplication reduces unique chunk count, directly shrinking the `chunks_vec` index and accelerating KNN search. Cross-document deduplication stores identical paragraphs (boilerplate, headers, legal clauses) once. Garbage collection deletes chunks where `ref_count` reaches zero, paired with vector cleanup in `chunks_vec`.

## Integrated schema and ingestion pipeline

The unified architecture layers three optimizations without conflict:

| Layer | Storage | Key Parameters |
|-------|---------|----------------|
| Text chunks | `chunks.content` (BLOB, ZSTD + dict) | level 3, 100 KB dict per content type |
| FTS5 search | `chunks_fts` (external content) | uncompressed text for tokenization |
| Vectors | `chunks_vec` (vec0 virtual table) | `int8[384]` primary + `float[384]` rescore |
| Deduplication | `chunks.hash` (UNIQUE) + `ref_count` | BLAKE3, FastCDC min=512/avg=2048/max=4096 bytes |

CDC replaces line-based chunking at index time: `FastCDC::new(&content, min, avg, max)` yields chunks with tracked `line_start`/`line_end` for citation fidelity (Invariant #2). Vectors are quantized via `vq::ScalarQuantizer` trained on a sample, stored as `int8[384]` with float32 copies for rescoring. Dictionary training runs once per content type at index build; dictionaries persist in a `metadata` table and version with schema.

## Conclusion

The optimal algorithm is not a single technique but a composed pipeline: ZSTD dictionary compression for text, int8 scalar quantization with ADC for vectors, and FastCDC v2020 with BLAKE3 for deduplication. Each layer operates independently — text compression is invisible to FTS5, quantization is native to sqlite-vec, deduplication is enforced by a UNIQUE constraint — yet they compound multiplicatively. A 10 GB corpus of mixed documents shrinks to ~2–3 GB on disk; semantic search over 500k vectors runs in <50 ms p50 with 100% recall after rescoring. The entire stack compiles to a single Rust binary with zero C dependencies, satisfies `PAPER_OFFLINE=1`, and preserves exact line-number citations through CDC's boundary tracking. The only remaining tuning is empirical: optimal CDC chunk sizes for semantic boundaries, and dictionary retraining cadence for evolving corpora.
