# Windows per-user daemon + IPC for Paper (parity with launchd LaunchAgent / systemd --user)

Scope note: this covers the Windows daemon only. MCP registration is out of scope (Windows MCP clients spawn `paper mcp` over stdio; the daemon transport change does not affect it). Current state of the code, read during research: `src/cli/daemon.rs` renders a launchd plist and a systemd unit as pure functions (`render_launchd_plist`, `render_systemd_unit`), and every Windows path bails with `bail!("OS service installation is not yet supported on Windows; use Linux or macOS")`; `send_request` is `#[cfg(unix)]` with a Windows stub that bails ("daemon IPC is not yet supported on Windows"); `src/daemon/ipc.rs` is JSON-lines over a Unix socket with a peer-UID check (`SO_PEERCRED` / `getpeereid`); `src/bootstrap.rs` `ensure_service()` calls `install_service(false)` then falls back to `start_service()`, so on Windows the fallback cannot work either (both bail) and the state file is simply marked `Unavailable`. `Cargo.toml` pins `tokio = "1.38"` (features `full`), `notify = "8"`, `dirs = "5.0"`, `quick-xml = "0.42"`, `tracing-subscriber` (no file appender yet).

## Which autostart mechanism should a per-user, no-admin Windows daemon use?

### Takeaway
A **per-user Task Scheduler task with an at-logon trigger and an interactive token** is the only mechanism that gives launchd/systemd-user parity (start at logon, supervision/restart, query, run-now, clean uninstall) without admin rights. An SCM service is disqualified by UAC and by session 0; a `HKCU\...\Run` value or a Startup-folder shortcut is an acceptable *fallback* but has no supervision, no query, and no restart-on-crash.

### Cited Findings
- Task Scheduler can register `ONLOGON` schedules (`/sc onlogon`), and `/it` means "run the scheduled task only when the run-as user is logged on"; a verbose query then shows Logon Mode `Interactive only` — [schtasks create](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/schtasks-create).
- `/rl LIMITED` is the default run level ("least level of privileges, such as Standard User accounts"), and `/tr` "must not exceed 262 characters" — [schtasks create](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/schtasks-create).
- Scheduling anything that runs as **SYSTEM** or as another account requires elevation: "Only Administrators can schedule tasks, regardless of the value of the /ru parameter"; also "The System account doesn't have interactive logon rights" and schtasks "always prompts for a password unless you provide one" — [schtasks create](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/schtasks-create).
- The opposite case (task runs as the invoking user) is widely used without elevation: "You can absolutely create a tasks without admin rights, it's just local to your standard user account" — [Super User](https://superuser.com/questions/734968/how-can-i-run-a-task-scheduler-job-without-being-on-administrator-account); same conclusion in [Stack Overflow](https://stackoverflow.com/questions/10055516/scheduling-tasks-with-schtasks-without-admin-privileges-c-sharp) (plain `/Create /sc onlogon` from a standard user). (One blog reports `ACCESS_DENIED` for non-admins, but for PowerShell/`schtasks` combinations asking for elevated or "run whether logged on" registrations — [whenrebootingisnottheanswer](https://whenrebootingisnottheanswer.wordpress.com/2016/07/14/creating-a-scheduled-task-without-being-administrator/).)
- Since Windows Vista, services "cannot directly interact with a user", and "All services run in Terminal Services session 0"; Microsoft's own recommended pattern for user-facing work is a per-session process talking to the service over IPC (named pipes), with one pipe per session — [Interactive Services](https://learn.microsoft.com/en-us/windows/win32/services/interactive-services).
- Syncthing's official autostart page documents exactly two per-user Windows options: Task Scheduler at user logon (including setting "Start in") or a Startup-folder shortcut, with `--no-console --no-browser` — [Syncthing: Starting Syncthing Automatically](https://docs.syncthing.net/users/autostart.html).
- Tailscale, which needs a TUN adapter and route changes, installs a machine service and documents "unattended mode" for running when nobody is signed in; a maintainer states "Running tailscaled as a user isn't currently supported on Windows" — [Tailscale unattended](https://tailscale.com/docs/how-to/run-unattended), [tailscale#16257](https://github.com/tailscale/tailscale/issues/16257). This is the "needs admin because it needs a driver/device" class, which Paper is not in.
- Google's updater on Windows registers **per-user** scheduled tasks (`GoogleUpdateTaskUserS-1-5-21-…`) next to the machine-wide `GoogleUpdateTaskMachine*` ones — [Spiceworks thread](https://community.spiceworks.com/t/what-should-i-do-about-googleupdatetaskuser-in-scheduled-tasks/343580); Chromium confirms Chrome "auto-updates silently and without users needing to elevate" — [crbug 41324461](https://issues.chromium.org/issues/41324461).
- Ollama's Windows build has **no service at all**: users report `ollama.exe`/`ollama app.exe` "automatically launches via the Task Manager 'Startup apps' entry" and that no Ollama entry exists in `services.msc` — [ollama#10713](https://github.com/ollama/ollama/issues/10713).
- The Task Scheduler XML schema is the only way to set supervision details (`<Settings>`: `RestartOnFailure`, `MultipleInstancesPolicy`, `ExecutionTimeLimit`, `DisallowStartIfOnBatteries`, `StopIfGoingOnBatteries`, `StartWhenAvailable`) that `schtasks` flags do not expose — [Task Scheduler Schema](https://learn.microsoft.com/en-us/windows/win32/taskschd/task-scheduler-schema).

### Inferences
- Exact parity target is **logon**, not boot: launchd `RunAtLoad` in `gui/<uid>` and systemd `--user` `default.target` both start with the user session. `TASK_LOGON_INTERACTIVE_TOKEN` + at-logon therefore reproduces macOS/Linux behaviour rather than approximating it.
- "Run whether user is logged on or not" is *more* than parity and is unusable here: the no-password variant is S4U (needs the "Log on as a batch job" right, i.e. admin), the password variant needs a stored credential, and both move the process out of the interactive session where the user's `HKCU`, mapped drives and Explorer context live. Do not use it.
- Task Scheduler also gives the three things a `Run` key cannot: `RestartOnFailure` (≈ systemd `Restart=on-failure`, better than Paper's current launchd `KeepAlive=false`), `MultipleInstancesPolicy=IgnoreNew` (singleton), and `schtasks /query /xml` for locale-independent status.
- A `Run` key / Startup shortcut should remain implemented only as a degraded fallback for machines where Task Scheduler is policy-blocked; the bootstrap state machine already has an `Unavailable` state that could become `Degraded`.

### Gaps
- No fetched Microsoft statement of the form "a standard user may register a task that runs as themselves"; the evidence is the schtasks docs (only System/other-account cases require admin) plus practitioner sources. Treat the "non-admin can self-register a logon task" claim as high-confidence-but-not-officially-worded.
- Could not verify whether `schtasks /create` on a fresh Windows 11 build defaults `DisallowStartIfOnBatteries` to true; treat explicit XML settings as mandatory rather than relying on defaults.
- Everything, Docker Desktop, Dropbox, RustDesk were not verified from primary sources in this pass (see Gaps in the Ollama section for what was and was not read).

## Exactly how does Ollama's Windows build install, autostart, log, and relate the tray app to `ollama serve`?

### Takeaway
Ollama is the closest analogue and it is a **per-user Inno Setup install with a tray app and a Startup-folder shortcut, no Windows service**. The installer runs with `PrivilegesRequired=lowest`, installs to `%LOCALAPPDATA%\Programs\Ollama`, kills the running processes before copying (a locked `.exe` cannot be overwritten), and the app writes `app.log`, `server.log` and `upgrade.log` under `%LOCALAPPDATA%\Ollama`. A Windows service is explicitly *not* provided; the docs point at NSSM plus `ollama serve` for people who want one.

### Cited Findings
- `PrivilegesRequired=lowest`, `DefaultDirName={localappdata}\Programs\{#MyAppName}`, `CloseApplications=no`, `RestartApplications=no`, `DisableDirPage=yes`, `MinVersion=10.0.10240` — [app/ollama.iss](https://github.com/ollama/ollama/blob/main/app/ollama.iss).
- Upgrade/uninstall are stop-then-replace: `[Files]` entries carry `BeforeInstall: TaskKill('{#MyAppExeName}')` / `TaskKill('ollama.exe')`; the uninstaller runs `taskkill /im "ollama app.exe" /f /t`, `taskkill /im ollama.exe /f /t`, then `cmd /c timeout 5` with the comment "HACK! need to give the server and app enough time to exit" — [app/ollama.iss](https://github.com/ollama/ollama/blob/main/app/ollama.iss).
- Autostart artifact: the uninstaller deletes `{userstartup}\{#MyAppName}.lnk`, i.e. a per-user Startup-folder shortcut. There is **no** `[Registry]` `Run` value and no service registration in the installer — [app/ollama.iss](https://github.com/ollama/ollama/blob/main/app/ollama.iss). Consistent with users seeing it under Settings → Apps → Startup — [ollama#10713](https://github.com/ollama/ollama/issues/10713).
- Install is per-user, no admin: "The Ollama install does not require Administrator, and installs in your home directory by default"; after install "Ollama will run in the background and the `ollama` command line is available", API on `http://localhost:11434` — [Ollama Windows docs](https://docs.ollama.com/windows).
- Log/data layout: `%LOCALAPPDATA%\Ollama` = "logs, and downloaded updates" with `app.log`, `server.log`, `upgrade.log`; `%LOCALAPPDATA%\Programs\Ollama` = binaries (installer adds it to the user `PATH`); `%HOMEPATH%\.ollama` = models/config; `%TEMP%` = "temporary executable files in one or more `ollama*` directories" — [Ollama Windows docs](https://docs.ollama.com/windows).
- Service story: a standalone `ollama-windows-amd64.zip` exists for "running it as a system service via `ollama serve` with tools such as NSSM" — [Ollama Windows docs](https://docs.ollama.com/windows).
- The installer writes `HKCU\Environment` `Path` (append `{app}` when missing) and registers an `ollama://` URL protocol under `HKCU\Software\Classes` — [app/ollama.iss](https://github.com/ollama/ollama/blob/main/app/ollama.iss).
- The tray app is a separate GUI binary (`ollama app.exe`, built from `app/cmd/app`, launched hidden via `cmd /C set PATH=… & "ollama app.exe"` with `runhidden`) that supervises the server; the `app/` tree now contains `wintray/`, `server/`, `updater/`, `logrotate/` directories — [app/README.md](https://github.com/ollama/ollama/blob/main/app/README.md), [app/ollama.iss](https://github.com/ollama/ollama/blob/main/app/ollama.iss).

### Inferences
- Ollama's structural equivalent for Paper is: **installer-free per-user binary + a supervised logon task + a `--foreground` daemon mode**, with no tray (Paper has no UI, so the tray's only jobs — start/stop the server, show status, trigger updates — are covered by `paper daemon-control`).
- Ollama accepts a visible break in "same binary for CLI and daemon": `ollama app.exe` is a GUI-subsystem binary and `ollama.exe` is the console binary. Paper can avoid the split if Task Scheduler's console flash is solved (see the console-window question), otherwise the same split (a tiny `paper-app.exe` shim) is the proven escape hatch.
- Ollama's `--no-admin` positioning, `%LOCALAPPDATA%\Programs` install root, `HKCU\Environment` PATH edit, per-file `taskkill` before install, and separate `app.log`/`server.log` are all directly copyable patterns.

### Gaps
- The runtime code that (re)creates the Startup shortcut is not in `app/` any more (the tree was restructured into `app/cmd`, `app/server`, `app/wintray`, `app/updater`); only the installer/uninstaller evidence was read. Exact creation code (shortcut vs `StartupApproved` Run value) is unverified, though the `{userstartup}` uninstall entry is strong evidence for a `.lnk`.
- Ollama's updater internals (`app/updater/`) were not read: whether it renames the running image or re-runs the Inno installer is unverified. `%TEMP%\ollama*` temp exes plus `upgrade.log` and an `InstallDelete` of `%LOCALAPPDATA%\Ollama\updates` suggest staged download → stop → replace → restart.
- Docker Desktop, Dropbox, Everything and RustDesk behaviour was not verified from primary sources; do not cite them without a follow-up pass. (Docker Desktop is known to install a machine service plus a per-user UI, Everything's service is optional and admin-installed, RustDesk installs a service for unattended access — all admin-requiring, so they are weak comparables for a no-UAC design anyway.)

## Named pipes vs loopback TCP vs AF_UNIX, and which Rust crate?

### Takeaway
**Named pipes** (`\\.\pipe\paper-<user-SID>`, byte mode, JSON-lines, explicit DACL) with **`tokio::net::windows::named_pipe`** and **`windows-sys` 0.61** for the security descriptor. Pipes are the only transport that is (a) first-class async in Tokio on Windows, (b) kernel-scoped (no filesystem artifact, so no stale-endpoint cleanup), and (c) ACL-able per user and per logon session. Loopback TCP adds an unauthenticated local network surface; AF_UNIX is not exposed by Rust std or Tokio on Windows, so it means raw Winsock plus a second code path.

### Cited Findings
- Tokio's `named_pipe` module is "Available on **Windows and crate feature `net`** only", with `NamedPipeServer`, `NamedPipeClient`, `ServerOptions`, `ClientOptions`, `PipeMode`, `PipeEnd` — [tokio::net::windows::named_pipe](https://docs.rs/tokio/latest/tokio/net/windows/named_pipe/index.html) (Tokio **1.54.1**, docs.rs build 2026‑10‑21; it depends on `windows-sys ^0.61`).
- `ServerOptions`: default pipe mode is `PipeMode::Byte`; `first_pipe_instance(true)` makes a second server on the same name fail with `PermissionDenied`; `create_with_security_attributes_raw(addr, attrs: *mut c_void)` passes a raw `SECURITY_ATTRIBUTES` to `CreateNamedPipe`; "Remote clients are disabled by default" (`PIPE_REJECT_REMOTE_CLIENTS`); `max_instances` default is unlimited, hard cap 254 — [ServerOptions](https://docs.rs/tokio/latest/tokio/net/windows/named_pipe/struct.ServerOptions.html).
- Default named-pipe ACL (i.e. `lpSecurityAttributes = NULL`): "full control to the LocalSystem account, administrators, and the creator owner. They also grant **read access to members of the Everyone group and the anonymous account**" — [Named Pipe Security and Access Rights](https://learn.microsoft.com/en-us/windows/win32/ipc/named-pipe-security-and-access-rights).
- To isolate terminal-services sessions, "use the logon SID on the DACL for the pipe… it is the SID used to protect the per-session object namespace" — [Named Pipe Security and Access Rights](https://learn.microsoft.com/en-us/windows/win32/ipc/named-pipe-security-and-access-rights).
- Per-session pipe naming is the documented multi-user pattern ("the server can distinguish between multiple user processes by giving each pipe a unique name based on the session ID") — [Interactive Services](https://learn.microsoft.com/en-us/windows/win32/services/interactive-services).
- Tokio's Unix-domain sockets are Unix-only: `UnixListener`/`UnixStream` are documented "Available on Unix and crate feature `net` only" — [tokio::net::UnixListener](https://docs.rs/tokio/latest/tokio/net/struct.UnixListener.html). (Windows itself has AF_UNIX since 10/1803, but neither `std` nor Tokio exposes it on Windows, so it is raw Winsock or a shim.)
- Named pipes are Windows objects under `\\.\pipe\<name>` and exist only while an instance is open — [Named Pipes](https://learn.microsoft.com/en-us/windows/win32/ipc/named-pipes); the documented limit for the pipe name is 256 characters — [CreateNamedPipeW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-createnamedpipea).
- `interprocess` is the cross-platform abstraction route (named pipes on Windows, UDS/local sockets on Unix, with Tokio variants) — [interprocess crate](https://docs.rs/interprocess/latest/interprocess/); `windows-service` is the SCM route if a real service were ever needed — [windows-service crate](https://docs.rs/windows-service/latest/windows_service/).
- Ollama chose the opposite trade-off — an unauthenticated HTTP API on `localhost:11434` — and has a reported critical path-traversal RCE (CVE-2024-37032) — [docs](https://docs.ollama.com/windows), [NVD CVE-2024-37032](https://nvd.nist.gov/vuln/detail/CVE-2024-37032).

### Inferences
- Concretely for Paper: `let sid = current_user_sid_string()?; let name = format!(r"\\.\pipe\paper-{sid}");` — SID-based (not session-based) survives multiple sessions of the same user, keeps one daemon per user, and cannot collide across users. Keep the whole name far below 256 chars (SIDs are ~45 chars).
- Two-layer authorization, mirroring the existing `peer_uid()` logic: (1) explicit DACL granting `GENERIC_ALL` to the user SID and to `SYSTEM`, `PROTECTED_DACL_SECURITY_INFORMATION`, built with `InitializeSecurityDescriptor` + `SetEntriesInAclW` + `SetSecurityDescriptorDacl` (all in `windows-sys`), passed through `create_with_security_attributes_raw`; (2) after `connect()`, `GetNamedPipeClientProcessId` → `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)` → `OpenProcessToken` → `TokenUser` → compare SID. Layer 2 also replaces the Unix `SO_PEERCRED` check in `ipc.rs` under `#[cfg(windows)]`, so the "same UID only" invariant survives.
- One extra reason to prefer a per-user pipe over per-session: the documented logon-SID ACL exists precisely because "Everyone" can otherwise read the pipe *and* because session-scoped namespaces leak across RDP sessions. Owner-only DACL plus a SID-named pipe is simpler and strictly tighter.
- Frame with the existing JSON-lines protocol in byte mode. `PipeMode::Message` would break `AsyncBufReadExt::lines()` when a message exceeds the read buffer (message mode yields `ERROR_MORE_DATA` per read), and byte mode also lets `BufReader` coalesce small writes — both are required for the current `IpcClient::send`/`serde_json` line protocol to port unchanged.
- Server accept loop must be reshaped (a pipe instance serves exactly one client): create the first instance with `first_pipe_instance(true)`, `connect().await`, hand the connected instance to a task, then create the next instance *before* awaiting the next connection. `first_pipe_instance(true)` doubles as the singleton lock, which is strictly better than the Unix "socket file exists → is it alive?" dance.
- No stale-endpoint cleanup is needed at all: the pipe namespace entry disappears when the last handle closes, including on crash. That removes the `daemon.sock` leftover/`EADDRINUSE` class of bugs (and means the Windows code should *not* port the `remove_file(socket)` logic).
- `interprocess` is only worth it if you want one `#[cfg]`-free code path; it is a second abstraction over what Tokio already provides, and Paper's protocol is already hand-rolled, so the cheaper move is a ~40-line `transport` module with two `cfg` arms. Revisit if the Windows and Unix accept loops start to diverge.
- Loopback TCP should be rejected on threat-model grounds, not performance: any process of any user (and any web page via DNS-rebinding/CSRF to 127.0.0.1) can reach it; Windows provides no peer-credential equivalent for TCP that is as simple as `SO_PEERCRED`. Ollama is the cautionary tale.

### Gaps
- Exact `windows-sys`/`windows` crate versions for `Win32::Security::Authorization` helpers were not enumerated beyond "windows-sys 0.61" (the version Tokio 1.54 depends on); confirm the function set (`SetEntriesInAclW`, `ConvertStringSidToSidW`, `GetTokenInformation`) exists under those feature flags before committing.
- `interprocess`'s current version, message-mode/backpressure behaviour, and whether its Tokio named-pipe server enforces `first_pipe_instance` were not verified.
- No source found stating whether a `PROTECTED_DACL` on a pipe blocks an administrator from connecting; assume an admin/SYSTEM can still attach (grant them explicitly rather than relying on implicit access).

## How do you stop a console window flashing when the daemon is spawned?

### Takeaway
Never let a console-subsystem `paper.exe` be the direct action of a logon task or a UI-driven `Command::spawn`. Spawn it with **`CREATE_NO_WINDOW` (0x08000000)** from a parent that already exists (the first-run path in `bootstrap.rs`, `daemon-control start`, the updater), and if the Task Scheduler action itself must be flashed-free, point the task at a tiny **GUI-subsystem shim** (`#![windows_subsystem = "windows"]`) that immediately spawns `paper daemon --foreground` with `CREATE_NO_WINDOW` and exits. Do **not** flip the whole binary to the Windows subsystem: that detaches stdout from the console and breaks the CLI and the MCP stdio server.

### Cited Findings
- `CREATE_NO_WINDOW` (0x08000000): "The process is a console application that is being run without a console window. Therefore, the console handle for the application is not set. This flag is ignored if the application is not a console application, or if it is used with either `CREATE_NEW_CONSOLE` or `DETACHED_PROCESS`." — [Process Creation Flags](https://learn.microsoft.com/en-us/windows/win32/procthread/process-creation-flags).
- `DETACHED_PROCESS` (0x00000008): the child "does not inherit its parent's console"; it may later call `AllocConsole`; cannot be combined with `CREATE_NEW_CONSOLE` — [Process Creation Flags](https://learn.microsoft.com/en-us/windows/win32/procthread/process-creation-flags).
- `CREATE_NEW_PROCESS_GROUP` (0x00000200): "CTRL+C signals will be disabled for all processes within the new process group"; ignored with `CREATE_NEW_CONSOLE` — [Process Creation Flags](https://learn.microsoft.com/en-us/windows/win32/procthread/process-creation-flags).
- `CREATE_BREAKAWAY_FROM_JOB` (0x01000000): children "are not associated with the job… If the calling process is associated with a job, the job must set the `JOB_OBJECT_LIMIT_BREAKAWAY_OK` limit" — [Process Creation Flags](https://learn.microsoft.com/en-us/windows/win32/procthread/process-creation-flags).
- Rust's `std::os::windows::process::CommandExt::creation_flags(u32)` is the supported way to pass these from `std::process::Command` — [std::os::windows::process::CommandExt](https://doc.rust-lang.org/std/os/windows/process/trait.CommandExt.html).
- The `windows-subsystem` behaviour is what forces Ollama's split into `ollama app.exe` (GUI, launched `runhidden`) and `ollama.exe` (console) — [app/ollama.iss](https://github.com/ollama/ollama/blob/main/app/ollama.iss), [app/README.md](https://github.com/ollama/ollama/blob/main/app/README.md).
- `schtasks.exe` is itself a console program, so every `schtasks` call from a GUI/editor context is another flash source unless spawned with `CREATE_NO_WINDOW` — inference from the flag semantics above plus Syncthing's `--no-console` guidance for its own binary — [Syncthing autostart](https://docs.syncthing.net/users/autostart.html).

### Inferences
- Two distinct spawn sites, two different fixes: (a) **first run from an editor/CLI** → `Command::new(exe).args(["daemon","--foreground"]).creation_flags(CREATE_NO_WINDOW | CREATE_NEW_PROCESS_GROUP)`; (b) **logon task** → Task Scheduler allocates a console for a console-subsystem action, so either accept a one-off flash at logon or ship the GUI-subsystem shim as the task action.
- `CREATE_NO_WINDOW` also solves the Ctrl+C problem for free: with no console attached the daemon cannot be hit by a `CTRL_C_EVENT` aimed at the editor's console, which `CREATE_NEW_PROCESS_GROUP` alone would not fully prevent for grandchildren.
- `CREATE_BREAKAWAY_FROM_JOB` should be *attempted* for the first-run spawn (editors and IDEs commonly put children in a job object with kill-on-close, so without breakaway the daemon dies when the editor is force-closed), and the spawn retried without the flag on `ERROR_ACCESS_DENIED`, because the flag is fatal when the job lacks `JOB_OBJECT_LIMIT_BREAKAWAY_OK`.
- A `windows_subsystem = "windows"` shim keeps the split to one extra ~30-line `[[bin]]`, which is cheaper than a tray app and gives a natural home for the "start hidden and exit" semantics. Alternative single-binary trick (attach to parent console only when one exists, `windows` subsystem + `AttachConsole(ATTACH_PARENT_PROCESS)`) is fragile for MCP stdio and should be rejected.
- Consequence for `bootstrap.rs`: it should never `spawn` the daemon with inherited stdio; redirect to the log file or drop the handles, otherwise a detached daemon inherits a pipe that dies with the editor and every later `println!`/tracing write fails.

### Gaps
- No primary source confirms whether a Windows 11 Task Scheduler at-logon task whose action is a console `.exe` visibly flashes a window in every configuration; this needs an empirical check on a Windows VM (test both `TASK_LOGON_INTERACTIVE_TOKEN` and a GUI-subsystem action). The recommendation to ship a shim is a hedge against that uncertainty, not a confirmed necessity.

## Session 0 isolation, multiple sessions/RDP, logoff, and parent-process lifetime

### Takeaway
Because a per-user logon task runs **in the user's interactive session with the user's token**, Paper inherits exactly the launchd/systemd-user semantics: it dies at logoff, it can read the user's profile, and each concurrent session (console + RDP, or two RDP sessions) is a separate logon and therefore a **separate task instance**. Guard against duplicate daemons with `first_pipe_instance` + a per-user (SID-based) pipe name; do not rely on one-daemon-per-session.

### Cited Findings
- "All services run in Terminal Services session 0. Therefore, if an interactive service displays a user interface, it is visible only to the user who connected to session 0"; "Services cannot directly interact with a user as of Windows Vista" — [Interactive Services](https://learn.microsoft.com/en-us/windows/win32/services/interactive-services).
- Microsoft's multi-user guidance for exactly this shape: run a per-session client, communicate over named pipes, and if the pipe server must distinguish sessions, "give each pipe a unique name based on the session ID" — [Interactive Services](https://learn.microsoft.com/en-us/windows/win32/services/interactive-services).
- A logon-triggered task fires per logon, and `/it` restricts it to the run-as user being logged on ("Interactive only") — [schtasks create](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/schtasks-create).
- A task created as SYSTEM or as another account needs admin; the System account has no interactive logon rights — [schtasks create](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/schtasks-create).
- `first_pipe_instance(true)`: "creation of the first server instance succeeds, but creation of any subsequent instances will fail with `PermissionDenied`… intended to be used with servers that want to ensure that they are the only process listening" — [tokio ServerOptions](https://docs.rs/tokio/latest/tokio/net/windows/named_pipe/struct.ServerOptions.html).

### Inferences
- Logoff ⇒ task instance terminated (Task Scheduler ends interactive-token tasks at logoff). That matches launchd `gui/<uid>` and systemd `--user` shutdown, so "indexing stops when I log out" is expected, documented behaviour rather than a Windows defect. Say so in the docs.
- Duplicate-instance sequence on a second RDP session: task starts a second `paper daemon`; its `ServerOptions::first_pipe_instance(true).create()` fails with `PermissionDenied`; it should log "another paper daemon already owns `\\.\pipe\paper-<sid>`" and exit **0** (not an error — Task Scheduler would otherwise show a failed run). Task Scheduler's `MultipleInstancesPolicy=IgnoreNew` only prevents duplicates *within one task instance*, not across sessions, which is why the pipe guard is required.
- Because the pipe name is per user, not per session, the second session's `paper search` / `paper daemon-control status` clients talk to the first session's daemon — including across console↔RDP. That is desirable (one index, one SQLite writer) and is why the SID name beats a session-suffixed name.
- Edge case worth deciding explicitly: if the *only* logged-on session is an admin's elevated RDP session, the daemon runs elevated and writes files owned by the elevated token — a classic Windows footgun. Since Paper is per-user and never elevates itself, the task will be inherited at the integrity level of the logon, which is what the user gets from launchd/systemd parity anyway; document "do not run Paper elevated; the task is LeastPrivilege".
- Parent-exit: with a Task Scheduler-launched daemon there is no parent to outlive. For the first-run spawn path, `CREATE_BREAKAWAY_FROM_JOB` + `CREATE_NO_WINDOW` + no inherited handles is the whole fix; a `DETACHED_PROCESS` daemon whose parent dies is unaffected (no console, no job membership) as long as breakaway succeeded.
- Windows "Fast Startup"/hibernate resumes do not re-run logon triggers, and the daemon survives sleep; a `WM_POWERBROADCAST`/`powrprof` subscription is unnecessary — the existing scheduler tick will catch up on file changes, and the 5-minute scan backstop covers missed `ReadDirectoryChangesW` events during sleep.

### Gaps
- No fetched source describing exactly what Task Scheduler does to an interactive-token task on **fast user switching** (as opposed to logoff). Assume it is suspended/ended with the session, and verify if it matters.
- The claim "Task Scheduler terminates interactive-token tasks at logoff" is inferred from the `/it` semantics rather than stated verbatim in the schtasks page.

## Upgrades: how do you replace a running `.exe`?

### Takeaway
You cannot overwrite or delete a running image, but you **can rename it**, and that is the whole trick: download to a temp file on the same volume → verify hash → stop the daemon via IPC → `MoveFileExW(current, current+".old", MOVEFILE_REPLACE_EXISTING)` → `MoveFileExW(tmp, current, MOVEFILE_REPLACE_EXISTING)` → `schtasks /run` → verify the new version over IPC → delete the `.old` on the next start. Versioned install directories with a stable launcher (Squirrel-style) is the alternative if you ever ship a GUI installer; stop-then-copy with `taskkill` (Ollama/Inno) is the third and crudest.

### Cited Findings
- Ollama's installer never tries to overwrite a live image: `BeforeInstall: TaskKill('…')` on every `[Files]` entry, `taskkill /f /t` on uninstall, then `cmd /c timeout 5` "to give the server and app enough time to exit" — [app/ollama.iss](https://github.com/ollama/ollama/blob/main/app/ollama.iss).
- Ollama stages downloads rather than updating in place: `%LOCALAPPDATA%\Ollama` holds "logs, and downloaded updates" (`upgrade.log`), and `%TEMP%` holds "temporary executable files in one or more `ollama*` directories"; the installer deletes `%LOCALAPPDATA%\Ollama\updates` on install — [Ollama Windows docs](https://docs.ollama.com/windows), [app/ollama.iss](https://github.com/ollama/ollama/blob/main/app/ollama.iss).
- `CloseApplications=no` / `RestartApplications=no` / `RestartIfNeededByRun=no` in Ollama's Inno script — i.e. it deliberately opts out of the installer framework's Restart Manager file-in-use handling and does its own kill — [app/ollama.iss](https://github.com/ollama/ollama/blob/main/app/ollama.iss).
- `MoveFileExW` is explicitly in the list of path APIs that support extended-length paths, and `MOVEFILE_REPLACE_EXISTING` / `MOVEFILE_DELAY_UNTIL_REBOOT` are its documented flags — [Maximum Path Length Limitation](https://learn.microsoft.com/en-us/windows/win32/fileio/maximum-file-path-limitation), [MoveFileExW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw).
- Task Scheduler actions hold an absolute path and are started by `schtasks /run` with no working-directory inheritance guarantees, so the action path must remain valid across the swap — [schtasks create](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/schtasks-create).

### Inferences
- Correct self-update sequence for a cargo-dist style binary:
  1. `GET` `paper-x86_64-pc-windows-msvc.exe` + `.sha256` from the release; verify before touching anything.
  2. Write `paper.exe.new` **in the same directory** (same volume — `MoveFileEx` across volumes degrades to copy+delete and loses atomicity).
  3. `paper daemon-control stop` (IPC `Shutdown`), wait for the process handle to signal (or `schtasks /end` + wait), with a 10 s timeout then `TerminateProcess`.
  4. Rename current → `paper.exe.old-<version>` (`MOVEFILE_REPLACE_EXISTING`); this succeeds even if a stale handle still maps the image.
  5. Rename `paper.exe.new` → `paper.exe`.
  6. `schtasks /run /tn Paper`; poll `paper daemon-control status --json` for the expected version; on mismatch/timeout, rename `.old` back and report.
  7. On every startup, delete `paper.exe.old-*` older than the running version, ignoring sharing violations.
- Antivirus/Defender scanning of the freshly written `paper.exe.new` can hold a share lock for a few hundred ms; every `MoveFileEx` should be retried 3–5 times with 100–500 ms backoff, and `MOVEFILE_DELAY_UNTIL_REBOOT` used only as the last resort (it writes to `PendingFileRenameOperations` and needs no admin for files the user owns, but it means "the update lands on next boot").
- Do not attempt `fs::write` over the live exe: it fails with a sharing violation and, worse, can truncate on some paths. Do not spawn a copy of the updater from `%TEMP%` either — that is exactly the pattern Defender flags (and what Ollama does, with `%TEMP%\ollama*` leftovers).
- A rollback must also restore the task registration if the update changed the install path; simplest is to never change the path (fixed `%LOCALAPPDATA%\Programs\Paper\paper.exe`, version only in the file's resources).
- MSI/WiX is the wrong tool here: per-user MSI (`ALLUSERS=2`, `MSIINSTALLPERUSER=1`) works but drags in Restart Manager UI and an installer dependency for a single static binary; cargo-dist + a self-updater (or `cargo-binstall`/`winget` for install) is closer to the project's "one binary" constraint.

### Gaps
- Could not verify Ollama's updater internals (`app/updater/`) — whether it renames the image or relaunches the Inno installer. The recommendation above is derived from Windows file-locking behaviour and from Ollama's visible staging/`taskkill` strategy, not from reading its updater source.
- No primary citation was collected for "renaming a running `.exe` is permitted while deleting it is not"; this is well-established Windows behaviour (the image section holds the file, and the loader opens it with delete-sharing for rename) but should be validated with a one-line test on the Windows runner before the design depends on it.

## Windows file watching at scale: `ReadDirectoryChangesW`, `notify`, and whether a rescan is mandatory

### Takeaway
A **periodic scan is mandatory**, not optional. `ReadDirectoryChangesW` explicitly reports buffer overflow by returning success with zero bytes and telling you to enumerate the tree; `notify` documents that large watches "may fail to receive all events"; and on Windows a directory watch **ends** when the watched directory is renamed or deleted, requiring a rewatch. Paper already has a 5-minute scheduler tick, so the cheapest correct design is: notify for latency + the existing tick as a full stat-walk reconciler + an immediate rescan whenever an overflow/error event or a watched-root removal is observed.

### Cited Findings
- Overflow semantics: "If the buffer overflows, ReadDirectoryChangesW will still return true, but the entire contents of the buffer are discarded and the lpBytesReturned parameter will be zero… In this case, you should compute the changes by enumerating the directory or subtree." Also `ERROR_NOTIFY_ENUM_DIR` when "the system was unable to record all the changes", and the same enumerate-the-subtree remedy — [ReadDirectoryChangesW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-readdirectorychangesw).
- Network limits: the call "fails with ERROR_INVALID_PARAMETER when the buffer length is greater than 64 KB and the application is monitoring a directory over the network"; fails `ERROR_NOACCESS` if the buffer is not DWORD-aligned; fails `ERROR_INVALID_FUNCTION` if the redirector/filesystem does not support it — [ReadDirectoryChangesW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-readdirectorychangesw).
- `notify` 9.0.0 (docs.rs build 2026‑11‑21) documents a Windows row in its backend table: for a **directory** watch, rename/move reports "old object, old paths", delete means "watch ends", and a new item at the original path needs "rewatch required"; for a **file** watch the original path is kept — [notify crate docs](https://docs.rs/notify/latest/notify/).
- notify explicitly disclaims completeness: "When watching a very large amount of files, notify may fail to receive all events. For example the linux backend is documented to not be a 100% reliable source" — [notify crate docs](https://docs.rs/notify/latest/notify/).
- `PollWatcher` is the documented fallback for unreliable native events, with `Config::with_poll_interval` (default 30 s) and `with_compare_contents` — [notify crate docs](https://docs.rs/notify/latest/notify/).
- The current Paper watcher already uses `RecommendedWatcher`, `RecursiveMode::Recursive`, and has explicit `unwatch`/re-`watch` paths (`src/daemon/watcher.rs`), i.e. the rewatch-on-removal hook exists but is driven by observed events, not by a guaranteed reconciler.

### Inferences
- Because `notify` does not surface `ERROR_NOTIFY_ENUM_DIR`/zero-byte overflow as a first-class "you missed events" signal on all backends, Paper cannot rely on the watcher to tell it that it is stale. A version-stamp + mtime/size stat walk on the scheduler tick is the only correctness backstop; the existing `unchanged` counter in `IndexStats` is already the right primitive.
- On overflow the correct action is *not* a full reindex: a stat-only pass (mtime+size, unchanged → skip) reconciles in seconds and is already implemented; only never-seen or changed files get re-chunked.
- Recursive cost on Windows is acceptable because `bWatchSubtree=TRUE` watches a whole tree from one root handle, so the number of handles scales with *roots*, not files. The expensive part is buffering events for a huge tree during a bulk copy, which is precisely the overflow case → size the buffer generously and keep the rescan.
- Practical Windows-specific filters to add: skip `FILE_ATTRIBUTE_REPARSE_POINT`/junctions to avoid loops and double-indexing (OneDrive/`Documents` redirection), and skip dehydrated cloud files (`FILE_ATTRIBUTE_RECALL_ON_DATA_ACCESS`/`OFFLINE`) so a scan does not silently hydrate gigabytes of OneDrive content. Neither is something `notify` will do for you.
- Case-insensitive dedupe is required: `C:\Users\Me\Docs` and `c:\users\me\docs` are the same root, and `std::fs::canonicalize` on Windows returns `\\?\C:\…` verbatim paths, so roots must be normalised (`dunce::simplified` or strip the prefix) before comparison and before storing them in `config.toml`.
- Network shares: if a user adds a UNC root, expect `ERROR_INVALID_FUNCTION`; degrade to `PollWatcher` for that root rather than failing the daemon.

### Gaps
- notify's per-backend buffer size on Windows (and whether it exposes it via `Config`) was not verified from source in this pass; the crate's `Config` has no documented Windows buffer knob on the docs page.
- No benchmark data for `ReadDirectoryChangesW` on a 100k-file tree was found; the "handles scale with roots" claim follows from `bWatchSubtree` semantics, not from a measurement.

## Log/data locations, rotation, and surfacing errors with no terminal

### Takeaway
`%LOCALAPPDATA%\paper` is the right home for DB, models, logs and the heartbeat (machine-local, large, rebuildable); `%APPDATA%` (Roaming) currently holds `config.toml` via `dirs::config_dir()` and should be reconsidered because roaming profiles would carry machine-specific roots between machines. With no terminal, errors must be surfaced through four channels: a rotated log file, the Windows Event Log for fatal startup failures, `schtasks /query /xml` "Last Result", and a heartbeat file that `paper daemon-control status` can read even when the pipe is dead.

### Cited Findings
- Known folders distinguish `FOLDERID_LocalAppData` (local, not roamed) from `FOLDERID_RoamingAppData` (roamed with the profile) — [Known Folder IDs](https://learn.microsoft.com/en-us/windows/win32/shell/knownfolderid).
- `dirs::cache_dir()` maps to `{FOLDERID_LocalAppData}` and `dirs::config_dir()` to `{FOLDERID_RoamingAppData}` on Windows — [dirs::cache_dir](https://docs.rs/dirs/latest/dirs/fn.cache_dir.html), [dirs::config_dir](https://docs.rs/dirs/latest/dirs/fn.config_dir.html). Paper's `Paths::new()` uses exactly these two, so today: DB/models/logs under `%LOCALAPPDATA%\paper`, `config.toml` under `%APPDATA%\paper`.
- Ollama's precedent for the same split: binaries and logs under `%LOCALAPPDATA%`, models+config under `%HOMEPATH%\.ollama`, three separate log files (`app.log`, `server.log`, `upgrade.log`) — [Ollama Windows docs](https://docs.ollama.com/windows).
- Task Scheduler records a per-run result and exposes it in a locale-dependent `schtasks /query /v` listing ("Last Result") and in the task's XML (`/query /xml`), plus the Task Scheduler operational event log — [schtasks create](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/schtasks-create), [Task Scheduler Schema](https://learn.microsoft.com/en-us/windows/win32/taskschd/task-scheduler-schema).
- Services/per-session processes with no console are expected to report problems out-of-band; Microsoft's documented options for talking to a user from a non-interactive context include `WTSSendMessage` (message box in the user's session) — [Interactive Services](https://learn.microsoft.com/en-us/windows/win32/services/interactive-services).

### Inferences
- Concretely: `%LOCALAPPDATA%\paper\logs\daemon.log` (+ `.1`, `.2`, size-capped, rotate *inside* the daemon by close→rename→reopen so no external reader can hold the handle), `%LOCALAPPDATA%\paper\health.json` written every ~30 s with `{pid, version, started_at, last_tick, paused, roots, indexed_files}`, and `ReportEventW` on `RegisterEventSourceW("Paper")` for the handful of fatal startup errors (port/pipe owned by another user, model dir unwritable, DB corrupt).
- `daemon-control status` should degrade in this order: IPC `GetStatus` → on connect failure read `health.json` and print "daemon not responding; last heartbeat N minutes ago (pid P, version V)" → on missing file read the last 20 lines of `daemon.log` → then `schtasks /query /tn Paper /xml` for `State`/`Last Result`. That is the only way "it silently stopped working" becomes diagnosable.
- Use `schtasks /query /xml` (not `/v /fo LIST`) for machine parsing: the XML is locale-independent and `quick-xml` is already a dependency, so no new crate is needed and no localised column names are parsed.
- Console-less output is a real hazard, not a theoretical one: a daemon launched by Task Scheduler has no valid stdout handle, and `tracing_subscriber`'s default writer swallows write errors — so a daemon configured with the CLI's stdout layer logs *nothing*. Daemon mode must install a file writer explicitly (via `tracing-appender` or a hand-rolled appender), and daemon code paths must avoid `println!` (which panics on a failed write).
- Keep `PAPER_HOME` authoritative for all of the above (tests and portable installs rely on it); the Windows task XML and log paths must be derived from `Paths`, not from `dirs` directly, or `PAPER_HOME` sandboxes will leak into the real profile.

### Gaps
- Did not verify whether `tracing-appender`'s rolling appender can rename an open log file on Windows when a second process (e.g. `paper daemon-control status` tailing it) holds a read handle; Rust's `File::open` does not request `FILE_SHARE_DELETE`, so a tail can block rotation. Needs an empirical check or the hand-rolled close-rotate-reopen loop.
- No source consulted on Windows Event Log rate limits/registration requirements beyond the API names.

## Antivirus/SmartScreen/Defender risk and >260-character paths

### Takeaway
An unsigned, self-updating, file-watching binary that registers a logon task is a textbook persistence+updater heuristic, so **Authenticode signing is the single highest-value mitigation**, followed by never launching through `powershell`/`cmd` shims, never writing into `%TEMP%`, and keeping the task name/description human-readable. For paths, add a `longPathAware` manifest **and** use `\\?\` for file APIs, normalise verbatim paths before display/config, and keep the install path and pipe name short (the Task Scheduler `/tr` field caps at 262 characters).

### Cited Findings
- SmartScreen/Defender reputation attaches to the signing identity; unsigned downloads show the "Windows protected your PC" interstitial and require "More info → Run anyway" — [Microsoft Defender SmartScreen](https://learn.microsoft.com/en-us/windows/security/operating-system-security/virus-and-threat-protection/microsoft-defender-smartscreen/).
- `MAX_PATH` is 260 characters; extended-length paths need the `\\?\` prefix (or `\\?\UNC\` for UNC), are capped around 32,767 characters, and "relative paths are always limited to a total of MAX_PATH characters" — [Maximum Path Length Limitation](https://learn.microsoft.com/en-us/windows/win32/fileio/maximum-file-path-limitation).
- Long-path opt-in requires **both** `HKLM\SYSTEM\CurrentControlSet\Control\FileSystem\LongPathsEnabled = 1` and a manifest `<ws2:longPathAware>true</ws2:longPathAware>`; the registry value is cached per process after the first file call and is not reloaded — [Maximum Path Length Limitation](https://learn.microsoft.com/en-us/windows/win32/fileio/maximum-file-path-limitation).
- `schtasks /create /tr` "path name must not exceed 262 characters" — a hard limit on where the binary may live — [schtasks create](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/schtasks-create).
- Ollama's per-user install root (`%LOCALAPPDATA%\Programs\Ollama`) and `%TEMP%\ollama*` staging are exactly the two locations AV heuristics watch most closely — [Ollama Windows docs](https://docs.ollama.com/windows).

### Inferences
- Signing: an OV code-signing certificate is the minimum; SmartScreen reputation accrues per certificate over download volume, so the first weeks after signing still warn. EV certificates are widely reported to grant immediate reputation, but Microsoft does not document that, so treat "EV = instant trust" as folklore and plan for a reputation ramp either way. Also submit the binary to Microsoft's false-positive portal after each release if Defender flags it.
- Behavioural hygiene that measurably reduces flags: one persistence mechanism only (the Task Scheduler task — do not *also* write `HKCU\Run`), no `-EncodedCommand`, no `powershell`/`wscript` launchers, no UPX/packing, no self-extraction to `%TEMP%`, signed installer *and* signed inner binary, and a task description like "Paper — indexes your documents locally" rather than an opaque name.
- Enterprise reality: AppLocker/WDAC default rules frequently allow execution only from `%ProgramFiles%` and `%Windir%`, so a binary in `%LOCALAPPDATA%\Programs` may be blocked outright. The daemon should therefore treat "task registered but `Last Result` = 0x80070005 / process never appears" as a distinct, actionable error ("blocked by application-control policy") rather than a generic failure. Controlled Folder Access is not a problem because Paper only reads user documents.
- Long paths: opt into `longPathAware`, but do not *depend* on the registry key being set by an admin — emit `\\?\` prefixes from `std::fs` call sites (Rust passes them through unchanged) and use `dunce::simplified()` when printing/storing/comparing, because `canonicalize()` hands back `\\?\C:\…` and that leaks into `config.toml`, log lines and task XML today.
- Pipe names are unaffected by `MAX_PATH` (they are not filesystem paths), but keep `\\.\pipe\paper-<sid>` short anyway; the documented name limit is 256 characters and 45 of them are the SID.
- Install path recommendation: `%LOCALAPPDATA%\Programs\Paper\paper.exe` (Ollama's layout, ~55 chars) rather than a versioned directory, which both dodges the 262-char `/tr` limit and keeps the task action stable across upgrades.

### Gaps
- No measured data on Defender false-positive rates for this specific shape of Rust binary, and no primary source for the EV-certificate reputation claim (explicitly flagged as folklore above).
- Whether `longPathAware` in the manifest is enough for `notify`/`ReadDirectoryChangesW` handles opened by a third-party crate (which passes the path through `CreateFileW`) was not verified; `\\?\` is the safe belt-and-braces.

## What is the recommended end-to-end Windows architecture for Paper?

### Takeaway
Ship a **per-user, task-scheduled, named-pipe daemon** with a degraded `HKCU\Run` fallback: install path `%LOCALAPPDATA%\Programs\Paper\paper.exe`, task `Paper` (at-logon, interactive token, LeastPrivilege, `IgnoreNew`, `ExecutionTimeLimit=PT0S`, restart-on-failure, battery settings off), action = GUI-subsystem shim that spawns `paper daemon --foreground` with `CREATE_NO_WINDOW`, IPC on `\\.\pipe\paper-<user-SID>` with an owner+SYSTEM DACL and a peer-SID check, notify 9 + the existing tick as rescan backstop, logs+heartbeat under `%LOCALAPPDATA%\paper`, and a rename-and-restart self-updater. This is launchd/systemd parity with no admin and no UAC, and it is the same shape Ollama ships.

### Cited Findings
- The parity baseline Paper already emits: launchd plist with `RunAtLoad`, `KeepAlive=false`, `StandardOutPath`/`StandardErrorPath`; systemd unit with `Type=simple`, `Restart=on-failure`, `WantedBy=default.target` (`src/cli/daemon.rs`) — both pure renderers, i.e. testable without touching the host.
- Per-user registration is possible without elevation only for tasks that run as the invoking user — [schtasks create](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/schtasks-create), [Super User](https://superuser.com/questions/734968/how-can-i-run-a-task-scheduler-job-without-being-on-administrator-account).
- The exact Windows primitives to use are documented above: `CREATE_NO_WINDOW`, `first_pipe_instance`, `create_with_security_attributes_raw`, `PipeMode::Byte`, `GetNamedPipeClientProcessId`, `ReadDirectoryChangesW` overflow → enumerate, `MoveFileExW`, `longPathAware`.
- Ollama demonstrates the viable no-admin packaging envelope: Inno `PrivilegesRequired=lowest`, `{localappdata}\Programs`, `HKCU\Environment` PATH, `taskkill` before replace, `%LOCALAPPDATA%` logs, no service — [app/ollama.iss](https://github.com/ollama/ollama/blob/main/app/ollama.iss), [Ollama Windows docs](https://docs.ollama.com/windows).
- Syncthing demonstrates the documented Task Scheduler-at-logon path (and that "run a console binary hidden" needs an explicit flag/shim) — [Syncthing autostart](https://docs.syncthing.net/users/autostart.html).

### Inferences — concrete implementation plan
1. **`render_task_scheduler_xml(exe: &Path, sid: &str) -> String`** beside `render_launchd_plist`/`render_systemd_unit`, pure and unit-tested on every platform. Register with `schtasks /create /tn Paper /xml <file> /f` (the XML file must be **UTF-16LE with BOM**; `schtasks` rejects UTF-8). Settings: `LogonTrigger` for the user; `Principal` with `LogonType=InteractiveToken`, `RunLevel=LeastPrivilege`; `MultipleInstancesPolicy=IgnoreNew`; `ExecutionTimeLimit=PT0S`; `DisallowStartIfOnBatteries=false`; `StopIfGoingOnBatteries=false`; `StartWhenAvailable=true`; `RestartOnFailure` interval `PT1M` count 3; `Enabled=true`.
2. **`daemon-control` mapping**: `install` → render+register+`/run`; `uninstall` → `/end` then `/delete /f`; `start` → `/run`; `restart` → `/end` + `/run`; `status` → IPC first, then `health.json`, then `schtasks /query /tn Paper /xml` (parse with `quick-xml`); `stop` → IPC `Shutdown` (keeps the "graceful" semantics) with `/end` as the hammer. Every `schtasks`/`taskkill` spawn gets `creation_flags(CREATE_NO_WINDOW)`.
3. **`send_request` for Windows**: same JSON-lines protocol over `NamedPipeClient` with the existing 5 s timeout; map `ERROR_FILE_NOT_FOUND`/`ERROR_PIPE_BUSY` to the current "could not connect… start it with `paper daemon --foreground`" message (plus the task hint), so UX text stays identical across platforms.
4. **`ipc.rs` split**: introduce `current_peer_is_owner(&pipe) -> bool` as the Windows sibling of `peer_uid`, and an `accept()` that materialises a fresh server instance per connection. Keep the `getuid`/`getpeereid` code path untouched.
5. **`ensure_service()` on Windows**: register the task; if registration fails with access-denied/policy errors, fall back to `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` + an immediate `CREATE_NO_WINDOW` spawn, and set a new `ServiceState::Degraded` so `paper doctor` can explain the reduced supervision. This finally makes the doc-comment in `bootstrap.rs` ("fall back to a detached daemon for this login session") true.
6. **Watcher**: keep notify 8 (or bump to 9) for latency; on any error event or `RemoveKind` for a watched root, re-`watch` and schedule an immediate stat-walk; keep the 5-minute tick as the reconciler; add reparse-point and dehydrated-file filters.
7. **Self-update**: implement the rename-and-restart sequence above as `paper self-update`, with hash verification, retry-on-lock, `.old` cleanup at startup, and a version check over IPC after restart.
8. **Tests**: extend `tests/daemon_ipc.rs` with a Windows-only transport test (two clients, one daemon; second daemon exits 0 on `first_pipe_instance` conflict; a pipe created by another user is unreachable), and add XML-renderer snapshot tests. Keep `PAPER_HOME` sandboxing for everything so CI can run on `windows-latest` without touching the real profile.
9. **Docs**: update `docs/implementation-status.md` (it is the as-built source of truth per `AGENTS.md`) with the task XML, pipe name, log locations and the logoff semantics, and state explicitly that Windows parity is *per logon*, not per boot.

### Gaps
- No Windows hardware was available for this research; every behavioural claim (console flash, logoff termination, rename-while-running, `schtasks` UTF-16 requirement) needs a Windows 11 + Windows 10 22H2 verification pass before the design is treated as settled. The UTF-16 requirement for `/xml` is from field experience, not a fetched citation.
- COM (`ITaskService`) was not evaluated in depth; `windows-rs` exposes the Task Scheduler interfaces, but `schtasks /xml` + `quick-xml` covers the same ground with no COM apartment/locale baggage, so the cheaper route is recommended. If a future requirement appears (e.g. registering for all users, or querying `LastRunResult` without subprocesses), revisit COM then.
- Cross-user/multi-user behaviour on a shared machine (two users each with their own task and pipe) is designed but unverified; specifically, whether `schtasks /query /tn Paper` from user B can see user A's task (it should not, since tasks are ACL'd per creator) was not confirmed from a source.
